# Fix the Maestro and Playwright audit findings

## 1. Owner ruling

2026-10-19, verbatim:

> "Do an adversarial review of the audit, reviewing the plan and spec documents, ADRs, and the commise screens. Compare against the web app flows and user stories and acceptance criteria. Then fix all findings."

Earlier the same day:

> "I also want you to look at the tests too, to see if the tests are actually correct as well or even are valuable"

## 2. Summary

Four reports feed this plan. Three audited the flows (editor, library, shared and shell). A fourth, `combative.md`, attacked those three. A fifth, `matrix.md`, mapped every story to a web test and a Maestro flow.

What the reports cover:

- Editor flows: 35 flows (20 FIX, 3 MERGE, 1 DELETE, 11 KEEP).
- Library flows: 29 flows (16 FIX, 4 MERGE, 1 DELETE, 8 KEEP).
- Shared, auth, offline, shell and visual files: 45 files (22 FIX, 3 MERGE, 1 DELETE, 19 KEEP).
- `combative.md` rechecked each verdict against the code and the Maestro 2.6.1 jars. It confirmed most, corrected some fixes, refuted a few, and wrote a deduplicated fix list of 46 items. It also found nine more problems (M1 to M9).
- `matrix.md` found 20 gaps (G1 to G20) and 4 web final checks that cannot fail.

`combative.md` is the authority. If it corrected or refuted a fix from the first three reports, this plan uses its version. Nothing here is copied from the first three reports unless `combative.md` confirmed it.

The main classes of problem:

- **End checks the starting screen already passes.** The tab bar draws `Recipes` and `Discover` on every tab screen. So a wait for those words is met before anything happens. The editor Title field also holds the typed title. So a wait for the title is met by the editor itself, even when the save failed.
- **Taps dropped during an iOS push or a sheet slide.** A menu item runs only after its sheet closes. iOS ignores taps during a native push. Maestro never retries a dropped tap. A few of these pass falsely.
- **Checks that read a stale list.** An outbox delete does not refresh the lists (M3). So "draft gone" and "creates nothing" can read the cache.
- **Android checks that cannot fail.** A labelled `Pressable` with a `Text` child is two nodes. The child is never `checked` or `selected`. So `checked: false` always matches.
- **Flows CI never runs.** Some have stale reasons. Some have no seed. Some are web `test.fixme`.
- **Deletes and merges.** Eight flows are duplicates or prove nothing.
- **Web checks that cannot fail.** Locators that match nothing, and absence checks with no positive anchor.
- **Stories nobody tests.** Twenty gaps. Some are on one platform only.

## 3. Rules for every fix

1. Every replacement check must be shown to FAIL in the state before the action, on both platforms. Use a hierarchy dump or a mutant run. Do this on the first site. Apply it in bulk only after that.
2. A deleted flow names where its coverage went, in the commit message and in the table row.
3. In the same commit as any flow added, removed or re-planned, change all three of:
    - `FLOW_PLAN` in `packages/apps/commise/mobile/tests/e2e/runMaestroFlows.sh`
    - `packages/tools/repoGuards/__tests__/maestroFlowSelection.test.ts`
    - `packages/tools/repoGuards/__tests__/maestroPlatformExclusions.test.ts`
4. `common/scrollIntoTapView.yaml` is frozen. Do not edit it.
5. Deletions under `visual/` wait for the design peer.
6. Wait for the snackbar first, then for `notVisible: 'Close editor'` (combative G3 and M5). Give the second wait a timeout at least 20 s longer than the first (combative G1).
7. Wait on `My recipes`, never `Recipes`. Use `'<name>(, .*)?'` for iOS merged rows.
8. Do not write a stale-list assertion into a flow. Report it as an app defect (Group B).

Short names: `M/` is `packages/apps/commise/mobile/.maestro/`. `R/` is `M/recipes/`. `W/` is `packages/apps/commise/web/tests/e2e/`. `F/` is `packages/apps/commise/features/`.

## 8. Group D: every e2e suite reads its targets from one resolver (owner ruling 2026-10-19)

Owner ruling, verbatim: "the playwright tests, as with all e2e tests (including maestro) should provide the ability for
their remote sources to be overridden/changed by the environment in which they are running and by the actor (optionally -
the actor takes precedence over environment and environment takes precedence over defaults). The defaults should point to
localhost. Within the Github job runners, the environment should override the urls to point to the sandbox urls; if the
sandbox is not up then all e2e tests (which include playwright) should be skipped. When running the e2e tests (which
include playwright and maestro) locally, you as the agent can override the urls to point to things like the sandbox or
localstack or something else either through the CLI or via the environment."

staff-architect designed it on 2026-10-19 (PLAN + BLUEPRINT). The shape:

- One new package, `@kitchensink/e2e-targets`. It holds a registry of the remote targets (recipe, identity, food, web,
  remote search) and one pure resolver. Precedence per target is a flag (`--e2e-<target>=`, `--e2e-stage=`), then the
  environment (`E2E_<TARGET>_URL`, `E2E_STAGE`), then a localhost default. In CI a default or loopback value is refused,
  a production origin is refused unless the suite allows it, and a mixed set of stages is refused.
- Mobile reads its targets at launch from Maestro launch arguments, through a local Expo module, behind a build flag that
  only the test-app build sets, with five production-safety layers. One test app then serves every PR.
- The 85 mocked web specs (about 407 tests) split: 362 convert to real services, 40 move down to vitest + RTL + MSW
  integration tests, 4 need a decision, and 1 is re-homed. The stubbed-API lane is deleted at the end.
- Guards: pass-through env equals the registry, default ports equal each service's own, no e2e source reads an origin
  outside the registry, every `launchApp` carries the launch keys, and a shrinking list of mocked specs that ends empty.
- ADR-0067 (Proposed) records it, and amends ADR-0032 section 7.
- Size: about 4 to 6 weeks of agent work in 10 steps, each leaving CI green.

Open questions for the owner, from the design:

1. During the migration, keep the stubbed-API lane running on every PR until the list of mocked specs is empty
   (recommended), or gate it on the sandbox at once?
2. Each batch PR needs one deployed run before merge, which needs Sandbox Up pressed by hand. Accept that cost?
3. The 4 layout tests that need data no service can produce: a local-only design-system check, or a pool lane with a
   60-character email?
4. May Vercel preview builds set `COMMISE_PSEUDO_LOCALE=1`, for the `controlLabels` spec?
5. Add a web erasure lane to the pool, for `accountDangerZone`?
6. Keep `DATABASE_ADMIN_URL` and `AWS_ENDPOINT_URL` outside the resolver, with their fail-when-absent rule (recommended)?
7. With live services, should a preview's server HTML carry data or the loading frame (`ssrPrefetch`)?

Status: designed, not started. It starts after PR 91's CI is green. This section records the design's decisions. The full blueprint, with the draft ADR text, is kept outside the repo in `~/Development/ksAuditNotes/e2eTargetsBlueprint.md`. Step 0 commits it as ADR-0067.
