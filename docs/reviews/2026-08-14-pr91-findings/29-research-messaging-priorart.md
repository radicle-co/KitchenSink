# Research: prior art for fire-and-forget, per-group, full-history async status messages

**Problem restated:** backend services/Lambdas/workers emit async status messages, fire-and-forget. Messages group by entity (one import job, one food item). A consumer must read the FULL history for a group, not just latest. No message may be lost. Must be free-ish idle, scale to high volume without added latency. Context: solo developer, $300/mo AWS budget, near-zero traffic today, must scale later.

---

## Named patterns and when each is overkill

**Transactional outbox** — solves the dual-write problem: don't let "commit business state" and "publish notification" disagree when one can succeed and the other fail. Mechanics: write the message row in the _same DB transaction_ as the state change, then a separate relay (poller or CDC tailer) drains it to the real transport. Cost: a second table, a relay process/cron, dedup on the consumer (relay can double-publish if it crashes between publish and delete/mark-done) [microservices.io, docs.aws.amazon.com/prescriptive-guidance]. **Overkill when:** the "message" itself has no independent business meaning beyond notifying that a row changed — i.e., the row _is_ the durable fact and the message is disposable. Forcing an outbox+relay pair for a solo dev with near-zero traffic buys correctness you don't need because correctness already lives in the row (see dual-write section below).

**CDC (Debezium-style)** — reads the DB's write-ahead log and turns every row change into an event stream automatically, no outbox table needed. Real operational cost reported by teams who ran it themselves: "at least six systems" (Kafka brokers ×3+, ZooKeeper/KRaft ×3, Kafka Connect, Debezium connectors), Kafka+Java expertise required, and one mid-sized team's postmortem: "the operational and people cost ended up higher than anticipated... most changes still needed developers" despite a config-driven pitch [streamkap.com/self-managed-debezium-pain-points, 2026]. **Overkill for:** a solo developer — this is squarely in "don't run Kafka+ZK+Connect for one person's status feed" territory. AWS's own managed CDC path (DynamoDB Streams / RDS+DMS) is lighter but still adds a stream-processing hop you don't need if you can write the message directly.

**Event sourcing** — state is _derived_ by replaying the full event log; the log is the only source of truth, there is no separate "current row." Real value: audit trail, time-travel, natural fit when the log already needs to be authoritative. Real cost: eventual consistency for reads, snapshotting once the log gets long, and event schema evolution becomes a first-class problem. Explicit caution found: "CQRS and event sourcing are not top-level architectures... should be applied selectively in just a few places" [InfoQ panel, via search]; small teams can start light but the framework's own advocates warn against applying it as the default. **This is the overkill trap most relevant here** — the described problem ("read all messages for a group, don't lose any") sounds like event sourcing but isn't: nothing here requires _reconstructing current state by replaying events_. The current/authoritative state (job done, item validated) already lives in a normal row. What's wanted is an **audit/notification log**, not an event-sourced aggregate. Reach for event sourcing only if the plan is to ever derive current state purely from the log.

**Event log with compaction (Kafka-style)** — compaction keeps only the latest record per key, converting an append-only log into a changelog/table. Explicitly **wrong shape for this problem**: "a compacted topic cannot replay the original event sequence... anti-patterns include audit logs that require full history" [Confluent docs; oneuptime.com/kafka-log-compaction, 2026]. Since the requirement is "read ALL messages for a group," compaction is disqualified by definition — it would silently drop exactly the history being asked for.

**Inbox/outbox pair** — the inbox half (dedup table keyed by message id on the _consumer_ side) solves at-least-once delivery causing duplicate side effects. Only relevant here if a downstream consumer performs a non-idempotent action per message; if consumers just render history, skip it — YAGNI until a consumer does something that isn't idempotent.

**Per-entity event stream (DynamoDB partition=entity, sort=seq/timestamp)** — not a "pattern" from the literature so much as a direct data-modeling answer to the actual requirement. `PK=entityId, SK=timestamp#eventId` (or a monotonic version number) gives one cheap `Query` for "all messages for this group," preserves order, and needs no relay, no broker, no compaction decision. This is what several practitioner write-ups converge on for exactly this shape (see below) [github.com/alessandrobologna/dynamodb-event-store; AWS re:Invent DAT334 slides].

## The dual-write question (liveness vs. correctness — resolved)

Primary/authoritative sources agree on the core problem: writing to a DB and publishing to a broker are two independent operations with no shared transaction, so a crash between them leaves the two systems disagreeing — "one system has a record the other lacks" [Confluent, Wade Waldron, 2024-05-29]. The canonical fix is the transactional outbox (write the outbox row in the same DB transaction, relay separately) or CDC tailing the WAL, both surveyed identically by microservices.io and AWS Prescriptive Guidance.

Gunnar Morling's 2024-10-31 retrospective ("Revisiting the Outbox Pattern," decodable.co) is the most current authoritative take: outbox "continues to deserve a very central spot," rejecting both the "listen-to-yourself" alternative (publish-first, apply-locally-async — breaks read-your-own-writes) and Kafka's native 2PC (KIP-939 — trades outbox's single-resource-availability requirement for a two-resource one, net _less_ available). All of this literature, however, frames the dual-write problem as a **correctness** problem: the two systems must never disagree because _both_ are sources of truth that other systems act on (e.g., a payment service reacting to a "flight booked" event).

**That framing does not hold for this problem, and the distinction matters:** here, the relational row (or whatever holds the entity's current/authoritative state) is the _only_ thing anything depends on for correctness. The status message is a **notification of a already-committed fact**, read by a human/UI, not a trigger another service acts on transactionally. Losing a status message means a user sees a stale progress bar — a **liveness** failure (temporarily unavailable/stale information) — not a **correctness** failure (no other system's state becomes wrong, because nothing else derives durable state from the message). No source found frames it in exactly these terms, but it follows directly from the sources' own definition of the problem: outbox exists to prevent _two sources of truth from diverging_; if there is only one source of truth and the message is a side-channel echo of it, there is nothing to keep from diverging. **Conclusion: full transactional-outbox machinery (outbox table + relay + consumer dedup) is justified when the message drives another service's durable state (use it); it is not justified merely to avoid an occasional missed toast notification when the underlying row is already correct and durably written (write the message row directly, in the same transaction or immediately after, and skip the relay).** The one thing worth keeping from the outbox playbook regardless: writing the status row in the _same_ DB transaction as the state change it describes, so "job succeeded" can never be recorded without the corresponding status message existing (and vice versa) — that's a single insert, not a relay pipeline.

Where this could flip: if a downstream automation (not a human dashboard) starts _acting_ on the status messages transactionally (e.g., auto-retry orchestration keyed off "failed" events), the messages become a second source of truth and the full dual-write guarantee is back in scope.

## Real-world reports and migrations

- **SQS vs. Kinesis/DynamoDB for "read full history"**: multiple independent sources converge on the same structural fact — SQS is delete-on-consume ("once deleted, messages cannot be replayed... unsuitable for scenarios requiring historical replay or audit logs" — AWS SQS FAQ + community explainers), while Kinesis/DynamoDB Streams retain an ordered, re-readable log. This is exactly the "most queues delete on consume" discriminator the task called out, confirmed rather than assumed.
- **Debezium/Kafka self-hosting regret**: streamkap.com's 2026 writeup of a mid-sized team's Debezium+Kafka retrospective is the closest thing found to a postmortem: expected low-code CDC, got a 6-system operational burden and still needed developers for most changes. Directionally consistent with (but not the same team as) the DEV Community piece "Why We Replaced Debezium + Kafka in Our Large-Scale Real-Time Pipeline," which reports moving _away_ from that stack at higher scale for a different reason (throughput/latency at large scale) — i.e., people leave this stack both when they're too small for it and when they're big enough to need something more specialized; no source claims it's the right size for a solo developer.
- **DynamoDB-as-event-store implementations**: `github.com/alessandrobologna/dynamodb-event-store` and AWS's own re:Invent DAT334 deck describe the `PK=streamId/entityId, SK=version-or-timestamp` shape directly, with DynamoDB Streams/Kinesis layered on top only when _other_ consumers need push notification of new events — not needed just to store or query them.
- **DynamoDB pricing 2026** (bytebase.com, usage.ai, cloudzero.com, all 2026): on-demand mode has **zero idle cost** — "you pay zero when tables are idle" — plus a permanent (not 12-month) free tier of 2.5M read + 2.5M write request units/month and 2.5M stream reads. AWS cut on-demand pricing 50% on 2024-11-01. This directly satisfies "free-ish at idle, scales to high volume" — on-demand DynamoDB has no separate low-traffic tier to graduate out of; the same table and pricing model scales from zero to high volume without a re-architecture.

## Client push mechanisms

Evidence, not opinion, on WS vs SSE vs polling for exactly this shape (per-entity job/status progress):

- **GitLab, 2025-09-15** (about.gitlab.com): moved CI job-status polling (every 30s, 45.7M calls/day) to GraphQL subscriptions over WebSocket (ActionCable). Result: **92.56% reduction in calls** (3.4M/day), instant updates instead of up to 30s staleness, "no significant CPU or operational increases observed." This is a directly-on-point real production report for "per-entity job status push," and the improvement is the same shape independently reported elsewhere (a different, unnamed pipeline reported 45M→3.4M calls/day switching polling→WebSocket, ~92% reduction — likely the same underlying GitLab data point surfacing via aggregator, so treat as one source, not two).
- **SSE vs WebSocket, Ably 2026 comparison**: SSE runs over plain HTTP (works through corporate/firewall packet inspection where WebSocket upgrades sometimes don't; auto-reconnect built into `EventSource`), and is the better fit specifically when the server only pushes and the client never talks back mid-stream — which is exactly the "push status updates to a viewer" shape, not the "collaborative editing" shape. HTTP/1.1's 6-connections-per-origin cap on SSE is real but moot under HTTP/2 (multiplexed). No cost figures found in this source; a separate secondary source (medium.com/codetodeploy) claims "20-40% lower server resource cost for feed-based apps" with SSE vs WS but that number is unsourced/uncorroborated — treat as a single weak claim, not evidence.
- **Managed option**: AWS AppSync Events (GA, serverless WebSocket pub/sub) prices at **$1.00 per million operations** (connect, subscribe, publish, broadcast all counted), publish-over-WebSocket added 2025-03. This is a plausible "don't build your own WS fan-out" option that stays near-free at idle (pure per-operation billing, no fleet to keep warm) and scales without a re-architecture — matching the stated cost/scale constraint better than self-managed WebSocket infrastructure would for a solo developer.
- **Polling-with-ETag**: reduces bandwidth per request but a named source calls out precisely the shortfall relevant here — "you're still making constant requests, the server still processes each one, updates are still delayed by the polling interval." A commonly reported hybrid (poll while queued, upgrade to WS once running) is the pragmatic middle ground when full WS infra isn't justified yet.

**Synthesis for this axis:** at near-zero traffic, polling-with-ETag against the per-group history query is the cheapest possible thing and costs nothing idle; the moment update latency or request volume matters, the evidence (GitLab's own numbers) says jumping straight to a push mechanism (managed WS/SSE pub-sub, e.g. AppSync Events) rather than incrementally optimizing polling is what actually moved the needle in production, and it's a per-operation-billed service so it doesn't add idle cost either.

## Which shapes make per-group history cheap

The task named this as the real discriminator, and the sources bear it out cleanly:

| Shape                                                         | "All messages for group X" query | Why                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQS (any queue)                                               | **Impossible** once consumed     | delete-on-consume by design; no replay, no query-by-key [AWS SQS FAQ]                                                                                                                                                                                          |
| Kafka topic, default (time/size retention)                    | Expensive/awkward                | must scan the whole partition or rely on retention window; not indexed by entity                                                                                                                                                                               |
| Kafka topic, **compacted**                                    | **Actively wrong**               | keeps only the latest record per key — the full history is deliberately discarded [Confluent log-compaction docs]                                                                                                                                              |
| Kinesis stream                                                | Possible but bounded             | ordered and re-readable, but bounded retention (typically 24h–365d) and consumers must track shard iterators — not a "cheap single query," more a stream-processing job                                                                                        |
| Postgres append-only table, `WHERE entity_id = ? ORDER BY ts` | **Cheap**                        | one indexed query; standard relational tool for this exact shape                                                                                                                                                                                               |
| DynamoDB, `PK=entityId, SK=seq/timestamp`                     | **Cheap, single Query call**     | this is the textbook DynamoDB access pattern for "all events for one stream/entity," explicitly documented this way in AWS's own guidance and independent implementations [docs.aws.amazon.com/amazondynamodb/data-modeling-blocks; dynamodb-event-store repo] |

The pattern is consistent across every source: **whether "read all messages in a group" is cheap is a property of the storage shape (indexed-by-entity, append-only, no compaction/consumption-deletes it), not a property of which named architectural pattern (outbox/CDC/event-sourcing) wraps around it.** A DynamoDB table or a Postgres table with the right key gives the cheap query for free; a message _queue_ (SQS, or a broker used queue-style) structurally cannot, regardless of which delivery pattern sits in front of it.

## Synthesis: what the evidence supports

1. **Skip outbox/CDC/event-sourcing machinery.** The dual-write literature's own definition of the problem it solves (two independent sources of truth that must not diverge) doesn't apply — the row is the one source of truth, and the message is a disposable liveness signal about it. This is not a permanent exemption: it flips the moment something starts making durable, transactional decisions off the message stream itself, not off the underlying entity state.
2. **Store the status messages in a shape that makes "all messages for group X" a single indexed query**, not in a queue. DynamoDB `PK=entityId, SK=timestamp` (on-demand billing, zero idle cost, permanent free tier covering low volume, scales without redesign) or an append-only Postgres table (`WHERE entity_id = ? ORDER BY ts`, if already running Postgres for everything else) both satisfy this cheaply; a Kafka/Kinesis/SQS-based queue does not, and compacted logs actively violate the requirement.
3. **Write the status row from the fire-and-forget caller directly** (same transaction as the state change where the caller already holds one, e.g. a Lambda finishing work and writing both a state update and a status row) — no relay process needed, because nothing downstream requires the outbox's crash-atomicity guarantee.
4. **For client delivery, start with polling-with-ETag against the group-history query** (free at idle, no new infra) and graduate to a push mechanism only when volume/latency demands it — GitLab's own production numbers (92.56% fewer calls, instant vs. 30s-stale) are the evidence that this upgrade is worth doing, not a guess, but nothing here requires building it before it's needed. If/when it is needed, a managed per-operation-billed pub/sub (e.g., AppSync Events at $1/M ops) matches "free-ish at idle, scales to high volume" better than self-hosting WebSocket fan-out infrastructure would for a solo developer.
5. **Named-pattern vocabulary still applies, just narrower than it first looks**: this is "per-entity event log storage," not "event sourcing" (no state is _derived_ by replaying it) and not "transactional outbox" (no relay, no second source of truth to reconcile) — calling it either of those over-claims machinery the requirement doesn't need.
