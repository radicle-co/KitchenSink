## Decision record (owner rulings, 2026-07-18)

1. **Reconciliation tie-break rule (operative, replaces the "mockups canonical" slogan):** the mockup is the **floor** — the code MUST render at least what the wireframe shows. Retain any ratified-CR or clearly-superior shipped affordance the mockup lacks (additive). Where a shipped affordance **conflicts** with the mockup, it is an owner ruling case-by-case (as with L2/L3 the list card and D8 the "Custom" badge — both keep shipped behavior and amend the mockup). **This floor rule is copied verbatim into every child plan (W3/W5/W6/W7)** so a "match the wireframe verbatim" instruction can never silently subtract a shipped affordance the mockup omits.
2. **recipe-edit: REBUILD to the 4-step wizard** (Basic / Ingredients / Instructions / Photos) with Save-Draft / Preview / Publish and per-file photo status + retry (FR-001a).
3. **The three under-built FR surfaces are IN SCOPE now:** collection Pull-Updates preview + Clone + visibility (FR-010/011), version Compare/diff + Preview (FR-007b), conflict changed-only diff + A/B/C cards (FR-007c).
4. **recipe-list card: MERGE INTELLIGENTLY for optimal UX** — combine CR-001's difficulty/rating/PRO/servings with the mockup's cuisine tag, lead calories, tags, version badge, and visibility badge into one canonical card; update **both** the wireframe and the code to that merged design. **Note:** this card is the _same shared component_ rendered in the Home "recent recipes" widget — the reshape is in scope for the widget + its tests too (W1).
5. **Draft status: PERSISTED `recipes.status` column** (`NOT NULL DEFAULT 'published'`, `CHECK IN ('draft','published')`). This is a **security boundary**, not a UI convenience: a free-tier draft carries `visibility='public'`, so every public read predicate (search DAL, list, Community tab, collection-embed, clone eligibility, rating eligibility) MUST add `status='published' OR owner_id=caller`, and a draft MUST be **not rateable** (404, same as a tombstone). `status` is **orthogonal** to `deleted_at`. Decided in the master (W8-a) and settled **before** W1/W4, because it mutates the shared `Recipe` projection those workstreams consume.
6. **Author/editor handle: WRITE-TIME DENORMALIZATION — and the handle IS the existing `profiles.displayName` (doc-review ruling 2026-07-20).** No new identity concept: "by @handle" renders the identity service's `profiles.displayName` (already Clerk-synced via `user.updated` once S-I3 lands, and user-editable via `PATCH /v1/users/me`). No Clerk username enablement, no new JWT-template claim across the per-stage templates. The recipe service stores it denormalized on recipe + version rows at write time (initial value read from the local `author_handles` read model, falling back to the shared `deriveDisplayName(claims)` from `identity-core` — one rule, both services; see W8-a.2); the **rename-sync path** (mechanism in W8-a.2) is the authority that corrects drift — and it MUST fire on **both** displayName change routes: the Clerk `user.updated` webhook AND identity's `PATCH /v1/users/me`. Defined ONCE in W8-a; W4/W5/W6/W7 consume it. (Rejected: cross-service read-time lookup — a call on the hottest read paths; client-side join — duplicates the rule into every client; Clerk usernames — new identity surface + template changes for no product need.)
7. **Pull preview→commit: RE-DERIVE LIVE WITH DRIFT WARNING.** Commit always re-derives against the current source, and detects drift-since-preview by **recomputing the added/removed diff live and comparing it to the previewed diff the client echoes back** — catching both source drift AND the caller's own clone-membership change (a source-only marker misses the latter and would silently re-add a recipe the user just deleted from their clone). It then warns / re-previews before applying, so the user is never silently given a different set than they saw. (An optional source hash/marker may serve only as a fast-path; the authoritative check is diff-vs-previewed-diff. Full mechanism in W8-a.8.)
8. **S3 version archive is TRANSPARENT to users.** There is **no** user-facing "View in S3 archive" link and no exposed S3 URL. A user loads any prior version through the **normal** recipe API (`GET …/versions/{n}`), which **transparently falls back to S3** for versions evicted from the last-10 DB window. S3 is a cheap-storage implementation detail the user never sees. (This reclassifies V5 off "no new endpoint" — the snapshot GET gains S3-fallback behavior.)

## W9 — Frontend architecture & code-quality remediation

**Source:** adversarial frontend review (2026-07-18) — six grounded lenses (component architecture, React 19 anti-patterns, React-Native/cross-platform, monorepo boundaries + TypeScript, performance, a11y/security) + a verification pass that killed the false positives (recorded below so they are never re-raised). **Per the doc-review ruling (2026-07-20), W9's execution batches (the transport pass, the P1–P3 seams, etc. — per the master program order) each get their own child plan via `superpowers:writing-plans` before implementation, like W3/W5/W6/W7.**

**Standing design principles (owner-mandated — apply to EVERY component task in W1–W9, and gate review):**

1. **Render-component pattern, ONE responsibility.** Presentational components are pure `props → JSX`: no data/mutation/side-effects, and each does exactly one thing. If a component renders two materially different things, split it and let the container/orchestration choose which to render.
2. **Boolean/mode props MUST NOT switch behavior.** A boolean (or `mode`) prop that changes what a component _does_ — not just a display string/class — is an anti-pattern; the branch belongs in the **orchestration** component, which selects the right render component (or passes a discriminated-union variant). Pure display derivations from a state prop (label text, `aria-current`, active class) are fine; behavior/structure switches are not. See **B15**.
3. **Avoid refs.** A ref is permitted ONLY for a genuine external, non-declarative system with no alternative. A ref used to guard a state-sync effect, to mutate during render, or to reset an uncontrolled input is a code smell hiding a systemic issue — replace it (usually `key`-remount, lifting state, or a library like Radix). See **B14**.
4. **Patterns are the default language, not a last resort.** A high-quality codebase is _built_ with design patterns — they are the shared vocabulary for organizing, modeling, and orchestrating code, and extensibility/modularity come with them practically for free. Use a pattern whenever the use-case is what the pattern solves (the only misuse is _forcing_ one onto a mismatched shape). Prefer — and _compose_ — container/presentational, compound components, discriminated-union render maps/registries (as the Home widget surface already does), statecharts, specifications/policies, headless hooks (**B4**, **P1–P3**), and repository read seams (**P5**) over ad-hoc conditionals and duplication. Library-first (Radix, ky, Intl, zod, Expo Router/react-navigation, `expo-image`) over reinvention (**B6/B13**). The full target architecture is **W9-f**.
5. **Pattern-first communication (owner directive, now in CLAUDE.md §Design-pattern-first development).** Every W1–W9 PR description and code review LEADS with the design patterns used/introduced/affected and how they compose, before line-level detail; component/module JSDoc names the pattern(s) implemented; reviews reject unnamed ad-hoc shapes where a fitting pattern exists. Pure functions + pure components are requirements, not preferences.
