# W5 — Collection View: Pull-Updates, Clone, Visibility Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the collection-view surface up to its wireframe floor (CR-003 / FR-010/011): source-provenance metadata, a Pull-Updates preview→commit flow, Clone, a premium-gated visibility toggle, richer member rows and header, a clone-info panel, a web Back affordance, and pagination — on **both** web and mobile.

**Architecture:** The heavy backend contracts (draft-`status` boundary, S-R3 predicate module, author-handle denorm+sync, read-path 404/IDOR, the read-only pull-**preview** endpoint + drift-guarded commit) are already shipped and are consumed as-is. This plan adds (a) three **collection-detail DTO enrichments** the wireframe floor needs but the current DTO omits — `lastPulledAt`, frozen source attribution (`sourceOwnerHandle` + `sourceCollectionName`), and per-member `addedVia` on the embed; (b) the **recipe-service client SDK** surface for the already-existing preview endpoint + drift-echo; and (c) the **frontend** (feature-package presentational components composed by web/native containers). Member rows compose the existing `RecipeCard` + `RecipeCardModel` seam (extended with collection-row concerns), NOT a bespoke row and NOT a full `RecipeCard.*` compound refactor (that P7/W9-f refactor spans four surfaces and is out of W5's scope — see Global Constraints).

**Tech Stack:** NestJS 11 + Drizzle/PG16 (recipe-service), TanStack Query v5 typed client (`@kitchensink/recipe-service-client`), Next.js 15 / React 19 (web), Expo/RN 0.79 (`.native.tsx`), Radix UI (`Dialog`/`AlertDialog`), Vitest + RTL, Playwright (web e2e), Maestro (mobile e2e). Node 24.

## Global Constraints

_Every task's requirements implicitly include this section. Values copied verbatim from CR-003 / the master plan / the wireframe (`specs/001-commise-recipe-app/product-spec/wireframes/collection-view.md`)._

- **Reconciliation floor rule (master Decision 1):** the wireframe is the **floor** — the code MUST render at least what it shows. Retain any superior shipped affordance the mockup lacks (additive); never silently subtract. Where a shipped affordance conflicts with the mockup, flag it as an owner ruling, don't unilaterally resolve.
- **CR-003 trap — preview is a SEPARATE read-only endpoint, not `?dryRun`.** Preview = `POST /v1/collections/:id/pull-from-source/preview` (`@HttpCode(200)`, no write-rate-limit, structurally non-mutating). It returns `PullDiff { added, removed, unchanged }`. Commit = `POST /v1/collections/:id/pull-from-source` and MUST **echo the previewed diff** as the drift baseline. If the live diff disagrees, the server returns **409** (`pullDriftError`) — the UI MUST re-preview, never blind-retry.
- **CR-003 trap — visibility gate is the shared policy, never an inline tier check.** The Private option is premium-only via `canGoPrivate(viewer)` from `@kitchensink/recipe-core` (`recipeAccessPolicy.ts`). No inline `tier === 'premium'` anywhere in the UI. A free viewer sees Private disabled/gated with the upgrade affordance; toggling to public is always allowed.
- **CR-003 trap — source attribution is FROZEN at clone time (write-time denorm), not a read-time join.** Store `sourceOwnerHandle` + `sourceCollectionName` on the clone row at clone time (via `AuthorHandlesDal.findHandle(source.ownerId)` + `source.name`). This avoids a hot read-time cross-owner join AND avoids disclosing a source that went private/renamed after the clone. Attribution reflects "who I cloned from, as of the clone" — a source-owner rename does NOT retro-update it (documented, accepted; NOT wired into the handle-sync fan-out — YAGNI, no `sourceOwnerId` stored). `[View Source]` links by the existing `sourceCollectionId` and MUST degrade gracefully (source may 404/403 now).
- **`RecipeCard` composition, not a bespoke row and not a compound refactor.** Collection member rows render via the existing `RecipeCard` + `toRecipeCardModel` seam (`packages/apps/commise/features/recipes/src/card/`), extended to carry the collection-row concerns (`addedVia` source-indicator, `by @handle`, `vN`, visibility, calories). Do NOT hand-roll a second row card. Do NOT refactor `RecipeCard` into a dotted `RecipeCard.Cover/.Title/...` compound here — that P7/W9-f change spans list/widget/search/collection and is a separate workstream.
- **Cross-platform (enforced):** every user-facing change ships to web AND mobile in the same task. Shared logic/types/components live in the feature/shared packages; platform leaves use `.native.tsx` (never `.mobile.*`). A task is not done until both platforms have it and both have tests.
- **Localization:** every user-facing string goes through the messages/`useMessages` path — no hard-coded literals. New copy lands in the relevant `messages.ts`.
- **TDD (non-negotiable, §7.1):** failing test BEFORE code, per tier. Backend non-UI → unit AND integration. UI → a vitest component test for EVERY state (loading, empty, populated, error, gated, disabled), plus Playwright (web) AND Maestro (mobile) for each happy path. Services → e2e; k6 only where a new/changed HTTP surface warrants it (this plan adds no new service endpoint — preview/commit already exist and are covered — so no new k6 is required; note this in the final review rather than skipping silently).
- **Standards:** backend files kebab `name.type.ts`; frontend camelCase/PascalCase. Named exports only. `.js` on aliased imports, `.ts(x)` on relative. `import type` for types. Bracket env access. ISO-8601 strings in interfaces. Strict TS, zero `any`, no `@ts-ignore`. `getByRole`/`getByLabel` only in Playwright; no `data-testid`, no `waitForTimeout`.
- **Node 24:** prefix commands with `export PATH="$HOME/.nvm/versions/node/v24"*/bin:$PATH`.
