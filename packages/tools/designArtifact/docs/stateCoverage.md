# Screen state coverage

This is the list of every screen state the apps render, and the board that shows it. Builders work from it.

It is an audit, not a design. It is not production code. It does not make any design calls. It shows what the code
does today and where the canvas has a gap.

## Summary

- **Surfaces:** 12 parts, split into 31 tables (one per surface or sub-surface).
- **States:** 385 rows. Of those, 45 already have a board, 13 are spoken only, 1 renders nothing, and **326 are
  MISSING** (fully or in part).
- **Boards that already show a state other than the happy path:** `RecipeVersionsEmpty`, and the 13 `FoodSearch*`
  pairs from `dfbe28a8f`. Every other board shows a filled, working screen.
- **Build list:** 134 entries (B-01 to B-134). 133 are web and mobile pairs, and B-126 is one missing mobile file.
  Three pairs draw on one platform only and use a captioned stand-in frame on the other: B-51, B-116, B-130.

## How to read this

- **Snapshot.** Code and boards as of commit `dfbe28a8f` (2026-10-17 13:23). That commit added 13 food-search board
  pairs. If more boards land later, check the board column again before you build.
- **Each table** lists one surface. Its columns are: the state, the real English copy, where the code picks or renders
  it, and the board that shows it.
- **"MISSING"** means no board shows the state. The code for "B-nn" (for example "MISSING → B-07") is the proposed
  board in the build list at the end.
- **"spoken"** means the copy is read only by a screen reader (`sr-only` or a live region). It has no visual. It needs
  no board of its own, but it is listed so no branch is dropped. Show it as a caption on the board that shows the
  visible twin.
- **"web only" / "mobile only"** marks a state that exists on one platform. Most states are shared, because
  `features/*` render both platforms from one model.
- **Source.** A cell with a line number points at the render or select site. A cell with no line number cites the
  module that selects the copy.
- **Boards.** A board name without `.dc.html` means the web file and its `…Mobile` twin. `FoodSearchX` is short for
  `RecipeEditorFoodSearchX`.

### How this list was built

1. Every English string in the 22 `messages.ts` catalogs was extracted by script (1,296 keys). The two auth catalogs
   in `a/` (`authBlockMessages.ts`, `authSurfaceMessages.ts`) were read by hand.
2. Each key was traced to the code that selects or renders it.
3. The state models were read wherever a state has no string of its own: `r/form/entryCombobox.ts`,
   `r/form/rowSecondLine.ts`, `r/form/ingredientRowPolicy.ts`, `r/form/shortlistPanel.model.ts`,
   `r/form/rowCommitMessage.ts`, `r/form/pasteStatusCopy.ts`, and the dialogs' `switch` statements.
4. Every board's visible text and props JSON was searched for each string's fixed part, in both directions.

Limits:

- Nothing was rendered. Board mapping is by copy, not by looking at the boards.
- Clerk renders web sign-in and sign-up, so their states are not in repo code.
- Copy with no render site (see the end) is not counted as a state.
- The script missed keys written in quotes (such as `'meal-plan'`). These were checked by hand. None of them is a
  state.

## Part 1. Food search and ingredient entry (recipe editor)

The same list model (`entryComboboxOf`, `r/form/entryCombobox.ts:372`) serves three fields:

- **The add field.** This is the trailing row. It sits at the foot of the Ingredients section on a new recipe **and**
  on an existing one.
- **A row in Change food.** This is an existing line that is being re-picked. Editing a recipe uses it most.
- **The row's own search.** This opens from "Find a food for this", or from "No match found" on a line with no food.

A row's list never offers "Create my own food" (`r/form/rowEntryField.ts:143`, `offersCreateOwnFood: false`). The add
field always offers it (`r/form/trailingEntryField.ts:94`). That is the only difference in what the list shows.
