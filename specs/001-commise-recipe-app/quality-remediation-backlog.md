Product of an **adversarial** three-front audit (two correctness reviewers + one test-quality reviewer,
each instructed to assume the code is fragile and prove it) measured against
[`docs/engineering/ENGINEERING_EXCELLENCE.md`](../../docs/engineering/ENGINEERING_EXCELLENCE.md). Every
item below is a _verified_ defect or a _demonstrated_ weak test (with the specific mutation it fails to
catch), not a style nit. This is the "loop until none of it is true" worklist; work it top-down and
**each fix ships with a test that would fail if the bug were present.**

**Premise check.** The claim "if-statements without braces / doesn't follow style" did **not** hold —
0 brace-less blocks, no `any`/`@ts-ignore`, clean imports (ESLint/oxlint/prettier enforce it). The
claims "many bugs" and "tests only scratch the surface" **did** hold, decisively — see below.

## Tier 0 — Live correctness/security bugs (fix code + add mutation-killing test)

- [x] **(P1, ADV-1/F15) Lost update: optimistic concurrency was a non-atomic TOCTOU.** `RecipesDal.update` WHERE had no version predicate → two same-base PATCHes both commit, no 409. **FIXED (eeb8b78):** atomic CAS `current_version = expectedVersion`; 0-row → re-read → truthful 409/404. Proven by `concurrent-update.integration.spec.ts` (racing PATCHes → exactly one 200 + one 409, winner persists; drop the predicate → 200/200 fails it).
- [x] **(P2, ADV-3/F2) `create` bypassed the C-004 visibility policy.** `create` persisted `dto.visibility ?? 'public'` with no gate → a free-tier user could POST `visibility:'private'` (violated FR-003). **FIXED:** `create` now takes the full `Principal`, derives `isPremium` from `permissions`, and runs the same pure `evaluateVisibility({sourceType:'user_created', hasSubstantiveEdit:false, requested})` the set-visibility endpoint uses — free-tier `private` → `INVALID_VISIBILITY` (400) _before_ any persistence; premium `private` allowed. Proven by 4 unit tests (free-tier private rejected + DAL never called; premium private persists; premium-in-scopes-not-permissions still rejected) + an end-to-end integration test (free-tier `POST {visibility:'private'}` → 400 + 0 rows; public → 201). Remove the gate → the rejecting tests resolve and fail.
- [x] **(P2, ADV-4/F1) Collection reads leaked other users' PRIVATE recipes (IDOR + stale visibility).** `findActiveRecipe`/`listRecipes` filtered only `deleted_at IS NULL` — no viewability predicate, so a user could add anyone's recipe to their own collection and `GET /collections/{id}` returned its full body; a recipe flipped private after being added stayed visible. **FIXED:** extracted the read-side rule into one pure, tested `isRecipeViewableBy(recipe, viewerId)` (`recipes/domain/recipe-visibility.ts` — `public OR owner==viewer`) and applied it as **defense in depth**: fail-fast at `addRecipe` (a non-viewable recipe → `RECIPE_NOT_FOUND`, existence not disclosed, no membership written) AND authoritative at read (`listRecipes(collectionId, viewerId)` SQL `visibility='public' OR owner_id=viewer`, which also catches the stale-visibility case add-time validation cannot). De-drifted `RecipesService.getById` onto the same predicate (was the 3rd hand-coded copy). Proven by the predicate's full truth-table unit test (**Stryker: 100%, 9/9 mutants killed**), 3 addRecipe authz unit tests, and 2 integration tests (add others' private → 404 + 0 memberships; a member that goes private after add drops from the listing). Remove either enforcement point → a test fails.
- [x] **(P2, ADV-2) Search text was client-poisonable / diverged from the catalog name.** `ingredient_names_text` (feeds `search_vector`) was built from the client DTO `name`, while the junction persists the catalog `ingredient.name` → a recipe displayed "All-purpose flour" but was indexed under whatever string the client sent (poisoning + unfindability). **FIXED:** `buildIngredientNamesText` now takes the RESOLVED catalog lines (`ingredientName`), not `dto.ingredients`, at both create and update call sites — the search index always tracks the persisted junction name. Proven by a unit test that sends a poison client name (`'zzz-not-a-real-name'`) for a catalog id and asserts the persisted `ingredientNamesText` is the catalog `'Onion'`. Reverting to `dto.name` fails it.
- [x] **(P2, verticals-3) Search facet sample was nondeterministic.** Facet CTE `ORDER BY rank DESC LIMIT 200` had no tiebreak, and `rank` is constant 0 in browse mode → EVERY row tied → arbitrary 200-row sample, facet chip counts flickered between identical requests and reflected a different slice than the page. **FIXED:** added a total-order tiebreak `ORDER BY rank DESC, created_at DESC, id` (newest-first, matching the page; the `id` PK guarantees a total order). Made `facetSampleSize` a constructor-injected knob (default `FACET_SAMPLE_SIZE`) so the sampling boundary is testable with a handful of rows. Proven by an integration test that injects sample size 2 over 3 rows with controlled `created_at`: the two newest (tag `keep`) are sampled and the oldest (`drop`) excluded, and two identical requests return identical counts. The test genuinely kills the mutation because the rows' insertion order differs from their recency order — dropping the tiebreak yields `{drop:1,keep:1}` ≠ the asserted `{keep:2}`.
- [x] **(P2, verticals-5/F8) Photo `reorder` accepted a non-permutation and corrupted `sortOrder`.** `photoIds:['C']` on a 3-photo recipe set C=0 and left A=0 → duplicate sort orders; duplicate/foreign ids compounded it. **FIXED:** extracted a pure, exhaustively-tested `isExactReorder(currentIds, requestedIds)` (`photos/photo-reorder.ts`) and enforced it INSIDE the DAL transaction — the current ids are read `FOR UPDATE`, validated as an exact permutation, and only then rewritten, so the check and the write are atomic (a concurrent add/delete can't reintroduce a gap). A non-permutation returns `null` (DAL stays HTTP-free) → the service maps it to 400. Proven by the predicate's Stryker-100% truth-table (13/13 killed), a DAL null-path unit test (writes nothing), a service 400 unit test, and 3 real-Postgres integration tests (full permutation reorders; partial + foreign-id lists → null with every `sort_order` left intact). The F8 _reorder_ half (cross-recipe reorder impossible) is covered by the foreign-id integration case; the F8 _delete_ half remains open.
- [ ] **(P3, verticals-9 — RECLASSIFIED to Tier-1; the original premise was FALSE) Search fabricates `servings: 0` for a null-servings row, which violates recipe-core `positiveIntSchema`.** `rowToRecipe: servings: row.servings ?? 0`. **Corrected analysis (2026-07-09):** the backlog's proposed fix ("preserve null — the schema already allows nullable servings") is WRONG — recipe-core `recipeSchema.servings = positiveIntSchema` (REQUIRED positive; 0 and null both invalid), so preserving null would itself violate recipe-core. The times are fine (`nonNegativeIntSchema` → `?? 0` is valid). The true defect is a **contract disagreement on servings nullability**: the DB column is nullable (`integer('servings')`, CHECK `>0` passes for NULL), the NestJS `RecipeResponse.servings` is `number | null`, but recipe-core `Recipe.servings` (used by the search path) is required-positive — and the create API requires `servings ≥ 1` (`@Min(1)`). _Dominant intent = servings is required-positive_; the nullable DB column + nullable `RecipeResponse` are the outliers. **Recommended resolution (needs the owner's contract call — it changes a wire contract):** backfill + `ALTER COLUMN servings SET NOT NULL` to match the create-required invariant, tighten `RecipeResponse.servings` to `number`, then delete the `?? 0` fabrication in search AND the sibling `?? 1` in `collections.toRecipe`. Do NOT ship a fabrication (0 or 1) as a "fix". Folds into the Tier-1 OpenAPI/contract reconciliation below.
- [x] **(P3, ADV-5) Catalog dedup was a read-then-insert race with no unique constraint.** Concurrent `createFreeform`/`createFoodBacked` both missed the SELECT and both INSERTed → duplicate catalog rows for the same `food_id`/name. **FIXED:** migration `0006_ingredient_dedup_unique.sql` adds partial UNIQUE indexes — `UNIQUE (food_id) WHERE food_id IS NOT NULL` (supersedes the old non-unique index) and `UNIQUE (lower(name)) WHERE is_user_entered = true` — mirrored in the Drizzle schema (`uniqueIndex`). Both DAL creates now `INSERT … ON CONFLICT DO NOTHING RETURNING`; an empty RETURNING (the race loser) re-selects and returns the winner's row. Proven by 2 race-path unit tests (insert no-op → re-read winner) + 3 integration tests (8-way concurrent `createFoodBacked` same food_id → exactly 1 row/1 id; 8-way concurrent `createFreeform` mixed-case same name → exactly 1 row; deterministic `23505` unique-violation on a raw duplicate insert). Greenfield (001 unshipped) so no duplicate backfill needed.

**✅ Tier 0 COMPLETE — all live correctness/security bugs fixed (ADV-3, ADV-4, ADV-2, verticals-5, verticals-3, ADV-5, P1 lost-update), each with a mutation-killing test; verticals-9 correctly reclassified to Tier-1 (false premise).**

## Tier 1 — Larger / architectural (decision + scope)

- [x] **(P1, verticals-1) Versions vertical was inert — no snapshot was written on create/update.** `createSnapshot` was only called by `restore`, so `GET /versions` was always `[]`, `restore` always 404'd, retention never ran. **FIXED:** `RecipesService` now records a version on every create/update/clone via a single best-effort `recordSnapshot` helper that builds a faithful `RecipeSnapshot` from the persisted aggregate and calls `VersionsService.createSnapshot` (which also runs retention). The `RecipesModule ↔ VersionsModule` cycle is resolved with `forwardRef` on both sides. `update` takes a `{ recordSnapshot }` option so `restore` (which drives an update AND records its own restore-provenance version) writes exactly ONE version, not two — enforced by the `(recipe_id, version_number)` unique. Snapshotting is best-effort (the recipe already committed, so a version hiccup is logged, not fatal to the save). Proven by 3 unit tests (create/update record; restore-path opt-out suppresses) + an end-to-end integration test (create→1 version; edit→2 newest-first; restore v1→content reverts + a 3rd version, no double) which also proves the forwardRef cycle boots. Adjusted the pre-existing retention spec to clear its auto-created v1 (it tests retention, not create's snapshotting). **Trade-off (honest):** the snapshot is written just AFTER the recipe tx commits (not inside it), so a process crash in the gap loses that one version — acceptable for an audit trail, backstopped by reconciliation; the fully-atomic in-tx variant (ARCH-BE-2) is the future hardening.
