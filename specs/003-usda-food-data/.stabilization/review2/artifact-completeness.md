## Findings

### M1 (MEDIUM) — REQ census arithmetic still inconsistent (100 vs 101)

`v-model/requirements.md` defines **19** non-functional reqs (REQ-NF-001..019), so the true total is
**63 FR + 19 NF + 12 IF + 7 CN = 101**. Residual stale "100"/"18 NF":

- `v-model/trace.md:41` — "63 FR + **18 NF** + 12 IF + 7 CN = **100** total"
- `v-model/trace.md:72` — "**100** REQ → 20 SYS"
  (yet `trace.md:538`/`:577` correctly say **101** — the file contradicts itself.)
- `v-model/release-audit-report.md:210` — "Requirement verification paths (**100/100**)"
  (yet that file's L36/67/86/145/259 correctly say **101**.)
  **Fix:** set NF=19 and total=101 at `trace.md:41` and `:72`, and `release-audit-report.md:210` →
  "101/101". The decision register §3.14 explicitly required fixing this census arithmetic; the fix is
  half-applied. Non-blocking (impl reads spec/plan/tasks, all consistent).

### M2 (MEDIUM) — `.forge-status.yml` declares a test-plan artifact that does not exist

`.forge-status.yml:214-216` records `test-plan: state: complete, artifact: testing/test-plan.md`, but
there is **no** `testing/` directory and no `test-plan.md` anywhere in the feature folder. This is
exactly the kind of overstated/stale status D-STATUS (§3.14) targets.
**Fix:** either create `testing/test-plan.md` or change the phase to `state: not-started`/`pending` with
`artifact: null` (the v-model test plans live under `v-model/`, so `test-plan: complete` pointing at a
phantom path is misleading). Non-blocking.

### L1 (LOW) — root `research.md` left un-reconciled and unmarked

`research.md` (root) still carries pre-design framing the register superseded: `ingredients` table +
`usda_fdc_id` (L394-396, 603), "Cache hit / Cache miss" (L394-395, 514-515), `FoodRequested`→SQS
(L395, 515), `fetch_status='fetched'/'pending'` (L396, 603) — under "Status: Complete" with **no**
superseded banner. The register reconciled the `research/` _subfolder_ (which got 2026-06-28 banners)
but did not list root `research.md`, so this is arguably a frozen pre-design input. Still, the asymmetry
(subfolder reconciled, root not, no banner) can mislead.
**Fix:** add a one-line "superseded by the source-agnostic stabilization baseline; see decision-register.md;
`fdcId`/cache/SQS/`fetch_status` framing below is pre-design exploration" banner at the top.

### L2 (LOW) — Product Forge version pin disagrees with the decision register

`decision-register.md §3.14` instructs "Update Product Forge version pins (`product-spec/README.md`
**v1.3.0**)", but `product-spec/README.md:12` and `.forge-status.yml` both say **v1.7.0** (and agree with
each other). The register's "v1.3.0" text looks like the stale element, not the docs.
**Fix:** reconcile — almost certainly correct the register's §3.14 pin to v1.7.0 (don't downgrade the
docs). Non-blocking, but a literal register-vs-artifact mismatch.

### L3 (LOW) — peer-review bodies retain pre-fix "FAIL/blocking" top-lines

Each of the 10 `peer-review*.md` has a correct 2026-06-28 reconciliation appendix, but the body above it
still reads the original verdict — e.g. `peer-review-requirements.md:19` "Overall assessment: **FAIL — 3
Critical / 4 Major**" and PRF-REQ-001 "**Implementation is blocked**", even though `requirements.md`
REQ-011/012 are now fixed and the appendix marks PRF-REQ-001/002/003 resolved. The register's stated
approach is "retain verbatim as the review record," and the appendix banner says it supersedes, so this
is by-design — but the unqualified FAIL with no inline pointer is a readability/staleness risk for anyone
reading top-down.
**Fix (optional):** add a one-line "⚠️ see Stabilization reconciliation appendix — verdict superseded"
note immediately under each Summary table. Informational.
