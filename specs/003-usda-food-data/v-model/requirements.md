## Overview

Integrate external food/nutrition sources as the data backing Commise recipes, behind a **source-agnostic
canonical model**. A food is keyed by an internal `id`; each external source (USDA wired today, others
additive) is a pluggable **adapter**. Users add foods **by name**; a background worker fans out across
every wired adapter, fetches from each source that has the item, normalizes the results, and **merges them
into a golden record** with per-field provenance — moving the food through `PENDING → (UNRESOLVED) →
RESOLVED` (terminal `NOT_FOUND` / `FAILED`). The system uses an event-driven, queue-based architecture
(Postgres `fetch_queue` + `LISTEN/NOTIFY` + a single Fargate fan-out/merge worker + a **per-source**
rolling-60-minute-window limiter) for rate-limited async resolution. Food data is served from a local
PostgreSQL store (Redis cache is a deferred variant) — no external source is ever called in the request
path. An add-by-name (cache miss) creates the canonical row + `id` up front and enqueues a sync via a direct
`fetch_queue` `INSERT … ON CONFLICT` + `pg_notify('fetch_queued', id)` → Fargate worker (EventBridge is NOT
on the demand path — it carries only scheduled producers and the `FoodDataReceived` completion event), and
each source is rate-limited to ≤ its own hourly budget in any trailing 60 minutes (USDA: ≤1,000).

## Assumptions

- **A-001**: Each external source's rate limit is a hard constraint. For USDA, the FoodData Central limit of 1,000 requests per hour per API key cannot be increased within the project timeline. Additional sources each bring their own limit, enforced by a per-source rolling window (REQ-019).
- **A-002**: The lean launch variant (no Redis; `kitchensink_food` database on the shared `kitchensink-data-{stage}` PostgreSQL instance) is the default starting configuration. Redis is the deferred variant, added when performance thresholds warrant it (p95 read latency > 100ms sustained, or read volume > 50K/day).
- **A-003**: Eventual consistency is acceptable for food data. Users tolerate a 10–60 second delay for first-time add-by-name resolutions in exchange for never blocking on an external source call.
- **A-004**: The USDA API remains publicly available with a free tier and the current `POST /v1/foods` batch endpoint supporting up to 20 IDs per request. USDA is the only wired source adapter at launch; the multi-source machinery is built now but a second concrete live source is out of scope.
- **A-005**: This feature deploys as an AWS-hosted backend service in `us-east-1`. The synchronous food read API is a NestJS service on ECS/Fargate fronted by the single shared per-stage ALB (host-based listener rule, priority 200; in-process Clerk auth middleware); the async resolution pipeline uses a Postgres `fetch_queue` with `LISTEN/NOTIFY`, a single Fargate fan-out/merge consumer worker (single instance via Postgres advisory lock), EventBridge scheduled producers (+ `FoodDataReceived`), and the `kitchensink_food` database on the shared `kitchensink-data-{stage}` instance (Redis is the deferred variant). It serves both the web and mobile Commise clients. The only API Gateway surface is the deferred WebSocket notifier (US-9), whose `$connect` Lambda authorizer is the sole authorizer-Lambda in the design — see REQ-043.
- **A-006**: This feature adds four packages to the KitchenSink monorepo (`@kitchensink/food-service`, `@kitchensink/usda-client`, `@kitchensink/food-service-client`, `@kitchensink/clerk-verify`), following all workspace governance rules from Constitution Principle V.
- **A-007**: Client-side polling (not WebSocket) is the launch notification mechanism. WebSocket (US-9) is deferred until UX testing validates the need.
- **A-008**: The canonical food schema is purpose-built for this feature. Integration with Commise's `ingredients` entity (a soft `food_id` link, no cross-database FK) is a downstream concern handled by feature `001-commise-recipe-app`.
- **A-009**: Each external source's API key (e.g. the USDA API key) is stored in AWS Secrets Manager and rotated per AWS best practices. Keys are never exposed in client-facing responses or logged. All food data HTTP API endpoints share the Commise application's authentication boundary, enforced in-process by the NestJS `AuthMiddleware` / `ClerkAuthService` on the ECS/Fargate service behind the ALB (networkless Clerk `verifyToken` + `azp`); there is no API Gateway / Lambda authorizer in the HTTP request path. No separate auth mechanism is required.
- **A-010**: All food data API endpoints use URL prefix versioning (`/v1/foods/*`), keyed on the internal `id`. Breaking changes (including response-contract and auth-semantic changes) require a new version prefix (`/v2/foods/*`) coordinated as a cutover. The USDA FoodData Central API's own `/v1/` prefix is independent and confined to the USDA adapter.
- **A-011**: Clerk token verification for the food read API is implemented in-process by a NestJS `AuthMiddleware` on ECS/Fargate behind a public ALB (same topology as the identity service), using the shared `ClerkAuthService` (`@clerk/backend` `verifyToken`, networkless). There is no API Gateway and no Lambda authorizer for the HTTP API; the verified `sub`/claims are populated on `req.user`. The only Lambda-authorizer / `$context.authorizer` surface is the deferred WebSocket notifier (US-9).
- **A-012**: Two Clerk token classes authenticate this service: user session tokens (interactive web/mobile callers) and machine (M2M) tokens (server-to-server callers — downstream services 001/006/007/009 and internal jobs). Both are verified networklessly via `CLERK_JWT_KEY` with `azp` enforcement; neither requires a Clerk secret key on the request path. Endpoints are classified user-token, service-token, or both (REQ-041).
- **A-013**: Lean launch reuses the shared single-AZ database instance (`multiAz: false`), so REQ-NF-017's 99.9% is a target with an accepted single-AZ risk, not a contractual SLA. Promoting `kitchensink-data-{stage}` to multi-AZ is the documented upgrade and is deferred to the GA/scale phase (T-061).
- **A-014**: A food's identity is the internal `id`; no source-native identifier is ever a key. `fdcId` and USDA terms are confined to the USDA adapter (`@kitchensink/usda-client`) and mapped to a generic `external_key` inbound. The merge/provenance/candidate machinery (golden record) is built now even though USDA is the only wired source, because the id/crosswalk foundation is the costly-to-change part. This is a clean replacement of the Phase 1–2 schema and API — **no data to migrate**.

## Glossary

| Term                   | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                   | A food's internal surrogate identity (ULID-valued, named `id`). The primary key of `food`, the queue key, and the poll handle. Never a source-native id.                                                                                                                                                                                                                                                                                                   |
| `external_key`         | A source's native key for an item (USDA `fdcId`, a barcode/GTIN), held as an attribute in the `food_sources` crosswalk — never a primary or foreign key in the canonical schema.                                                                                                                                                                                                                                                                           |
| `fdcId`                | USDA FoodData Central's native numeric identifier. Exists **only** inside the USDA adapter (`@kitchensink/usda-client`), mapped to `external_key` inbound.                                                                                                                                                                                                                                                                                                 |
| Food                   | A canonical, source-agnostic golden record keyed by an internal `id`. Distinct from a Commise Ingredient (a recipe component that MAY link to a Food via that Food's `id`; the link is optional).                                                                                                                                                                                                                                                          |
| Golden Record          | The merged, cross-source view of a food assembled by the fan-out/merge worker, with per-field provenance. Presence beats absence; higher-priority source wins identity/short fields and nutrient conflicts; longer value wins free-text.                                                                                                                                                                                                                   |
| Source Adapter         | A pluggable per-source client implementing the common `FoodSourceAdapter` interface (search-by-name, fetch-by-key, map-to-canonical). USDA is the only wired adapter; adding a source is additive.                                                                                                                                                                                                                                                         |
| Lifecycle Status       | A food's `status`: `PENDING` (created, queued) → `UNRESOLVED` (multiple candidates need a human) → `RESOLVED` (golden record assembled); terminal `NOT_FOUND` (no source has it, tombstone + TTL) / `FAILED` (a source errored after bounded retries, re-fetchable). Replaces the old `fetch_status` enum.                                                                                                                                                 |
| Candidate              | A normalized, per-source candidate produced during fan-out for an `UNRESOLVED` food, carrying its `source` and that source's item key. The user's `PATCH` pick must reference a candidate from the food's own candidate set.                                                                                                                                                                                                                               |
| Provenance             | The record of which source (and which source item) supplied each value: a `source_id` column on `food_nutrients`/`food_portions` and a thin `food_field_provenance(food_id, field, source_id)` side-table for scalar fields. No verbatim source payload is retained.                                                                                                                                                                                       |
| FetchRequest           | An intent to resolve a food from external sources; manifests as a `fetch_queue` row keyed on the food `id` (with a `NOTIFY` wake-up), or an `IngestionScheduled` EventBridge event for scheduled refresh.                                                                                                                                                                                                                                                  |
| RateLimitWindow        | A single source's rolling-window limiter state: recent source-call timestamps over the trailing 60 minutes and a derived `trailingCount` (capped at that source's limit; USDA cap = 1,000). Stored per source in a Postgres `source_call_log` (lean) or a per-source Redis sorted set (deferred). All check-and-record mutations are atomic. (Formerly TokenBucketState.)                                                                                  |
| QueueMessage           | A `fetch_queue` row in the food resolution pipeline containing `food_id`, `request_count`, `first_requested`/`last_requested`, `attempts`, `last_error`, and `status`.                                                                                                                                                                                                                                                                                     |
| FoodDataEvent          | A food data lifecycle event. EventBridge carries **only** `IngestionScheduled` (scheduled refresh) and `FoodDataReceived` (completion, carrying the food `id`); `FetchFailed` is emitted to CloudWatch/SNS on tombstone. `FoodRequested`/`FoodBatchRequested` are **not** EventBridge events — they denote the synchronous demand-path enqueue performed in-process by the read API directly against `fetch_queue` (`INSERT … ON CONFLICT` + `pg_notify`). |
| Tombstone              | A terminal food state: `NOT_FOUND` (no source has the item) or `FAILED` (sources errored after the retry budget), with the `fetch_queue` row `status='tombstone'`. Retained for a configurable TTL (default 30 days, REQ-018).                                                                                                                                                                                                                             |
| Lean Launch            | The default deployment variant: no Redis; `kitchensink_food` database on the shared `kitchensink-data-{stage}` instance; per-source rolling-window limiter state in the PostgreSQL `source_call_log`.                                                                                                                                                                                                                                                      |
| Full Architecture      | The deferred scaled variant: Redis for caching and the per-source rolling-window limiter (sorted set).                                                                                                                                                                                                                                                                                                                                                     |
| Tombstone Row          | A `fetch_queue` row marked `status='tombstone'` — the durable audit record for a `FAILED`/`NOT_FOUND` food (no SQS DLQ). Retained for the configurable tombstone TTL.                                                                                                                                                                                                                                                                                      |
| Rolling-Window Limiter | The per-source rate-limiting mechanism allowing ≤ that source's hourly cap in any trailing 60 minutes (USDA: ≤1,000); the worker pauses draining that source's work at 90% (USDA: 900) and resumes as earlier calls age out. State = recent source-call timestamps in a Postgres `source_call_log` (lean) or a per-source Redis sorted set (deferred).                                                                                                     |
| Pending-Set            | The deduplication mechanism tracking food `id`s currently queued for resolution (PostgreSQL `fetch_queue` `status='pending'` in the lean launch; a Redis Set in the deferred variant).                                                                                                                                                                                                                                                                     |
| Change-Driven Refresh  | The refresh model: a `RESOLVED` food's stored values stand; a background refresh updates a field only when its originating external source item has changed upstream (detected via `food_sources.item_version`), never blindly re-blending. Replaces stale-while-revalidate-by-age.                                                                                                                                                                        |
