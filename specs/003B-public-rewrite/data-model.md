# Data Model: Public Versions of Imported Recipes

Recipe database. One migration plus its `_validate` twin (next free numbers at build time). Expand-only (ADR-0035).
Owner, migrator and service roles per ADR-0039. Every one-way door below goes in the feature ADR before code.

## `recipe_source_records` (append-only, never shown)

One row per third-party import item (the page is `page_key`), written in the same transaction as the item's save or the job's creation. It is
the source of truth for this feature (FR-080). It extends ADR-0089 §6's evidence by reference and does not cascade from
a recipe, so it outlives the private copy and the public version (C-14). It holds no cook id: the job and the public version carry the
owner, and neither the fingerprint nor the monitoring count needs the cook. So erasure has nothing to sweep here, and the table goes
in `erasureSweepCoverage`'s `RETAINED_BY_RULING` map with this reason.

Indexes:

- `UNIQUE (page_key) WHERE state IN ('pending','writing','ready')`: one live job per source page. A second cook who collides is told there is a version on its way (`publicExists.writing`) and keeps Private. A job re-entering `pending` meets the same index, and a collision there answers `409 publicExists`.
- `(user_id, created_at)`: the cook's own job list.

The job points at its import item by the composite key: `FOREIGN KEY (import_item_import_id, import_item_ordinal) REFERENCES recipe_import_items(import_id, ordinal) ON DELETE SET NULL`, and `CHECK (num_nonnulls(import_item_import_id, import_item_ordinal) IN (0, 2))`, so the pair is both set or both NULL. Deleting an import (an explicit discard on the public-only path, below) deletes its header, its items and its lines by cascade, and the job's pair goes to NULL, so the job then has no item. No evidence row and no source-record row references the import item or the import header with `ON DELETE CASCADE`, so a discard never removes them.

Every expiry counts from `state_changed_at`, so a retry starts a fresh window. A job expires lazily, in the data layer, in the same transaction before an insert and again on every read: a job in
`pending` or `writing` for more than 10 minutes becomes `failed`. Every expiry from `pending` counts one attempt on the owner of the count (the item's `public_attempts` on the import path, the job's `attempts` on the later route), in the same UPDATE: `pending` is by definition unclaimed since it was entered, so there is no `claimed_at` test, and a retry loop that never reaches a worker, with the queue down, ends at 3. A job in `ready` for more than 24 hours becomes
`cancelled`, and so is a `checkRefused` or `failed` job after 24 hours, resting (fewer than 3 attempts) or final (3 attempts). A sweep on the band drain's existing 15-minute tick (`bandDrain.ts` in recipe-workers, beside `purgeFinishedImports` and the parse-job sweep) runs the same expiry function the reads use, and clears only the job's own text (`source_steps`, `facts_snapshot`, `output`) as it ends the job. It never touches the import item's draft, `recipe_import_items.payload`, which stays until Publish or keepPrivate clears it through `claimSave`, or until ADR-0072's 30-day purge removes it (FR-033). The sweep follows the lock order below: it locks the item `FOR UPDATE SKIP LOCKED`, then the job `FOR UPDATE SKIP LOCKED`, and re-checks the expiry under the lock. The lazy expiry inside reads and writes follows the same order: it reads the job's item key unlocked (the key never changes except to NULL), then locks the item and then the job. It follows ADR-0072's purge rules: its own transaction, `FOR UPDATE SKIP LOCKED`, and it runs even if an earlier sweep failed. Every tick publishes the age of the oldest expired job with `Stage` (ADR-0062), and a behind alarm, `PublicVersionJobSweepBehindAlarm`, is styled like `BulkImportPurgeBehindAlarm`. It adds no Lambda, no schedule rule and no NAT consumer. So a job nobody reads cannot hold its page key or its text: while the sweep runs, the job's text is cleared at most 73 h 15 min after Start, which is 3 x (20 min + 24 h) + 15 min: 3 attempts, each at most 20 minutes of work and 24 hours of rest, and one 15-minute sweep tick (FR-033). A sweep that runs late fires `PublicVersionJobSweepBehindAlarm`. A swept or expired import stays in To review in My recipes as an ordinary unfinished import (FR-044a).

Finished jobs are deleted 7 days after `finished_at` by the existing retention sweeper. The table is user-keyed: add it
to `erasureSweepCoverage` and to the test-principal purge.

## State transitions (job)

```text
pending ──claimed by worker──────────────▶ writing         (one attempt on the owner of the count, one writer call)
writing ──re-claim after a transport failure──▶ writing    (no attempt spent, state_changed_at unchanged, claimed_at updated, only while state_changed_at is within 10 minutes)
writing ──engine ok──────────────────────▶ ready           (output stored, reservation settled)
writing ──check refused, attempts < 2────▶ pending         (automatic retry)
writing ──check refused, attempts >= 2───▶ checkRefused    (rests while attempts < 3, final at 3)
writing ──ceiling denial─────────────────▶ budgetSpent     (refund, ack, never redelivered)
pending|writing ──10 min / maxReceive────▶ failed          (rests while attempts < 3, final at 3; every expiry from pending counts an attempt)
ready ──Publish (server re-checks pass)──▶ published       (same transaction as the recipe insert)
ready ──24 h─────────────────────────────▶ cancelled
ready ──"Write it again" (422 flags, 422 tooSimilar, 409 privateCopyChanged)──▶ pending   (attempts < 3)
checkRefused ──"Try again"───────────────▶ pending         (attempts < 3)
checkRefused ──24 h (attempts < 3)───────▶ cancelled
failed ──"Try again"────────────────────▶ pending         (attempts < 3)
failed ──24 h (attempts < 3)─────────────▶ cancelled
checkRefused|failed ──24 h (attempts = 3)────▶ cancelled        (the job's own text is already cleared)
pending|writing|ready|checkRefused|failed|budgetSpent ──cancel (on a saved item, the Both path and the later route: Stop, Back from the writing screen or from the review, review.notNowBoth, failed.done and the blocked and final exits; on the public-only path: Stop and review.discard, where the import is also deleted, and Back from the review calls no route)──▶ cancelled   (a late result is dropped: the result write needs state `writing` and the claim that wrote it, below)
pending|writing|ready|checkRefused|failed|budgetSpent ──keepPrivate (public-only path only, charges the unit)──▶ cancelled   (published answers 409 notKeepable)
```

Rules:

- The retry route (`POST /api/v1/public-version-jobs/{jobId}/retry`) makes `ready`, `checkRefused` and `failed` to
  `pending`. It answers `409 attemptsUsed` at 3 attempts. Re-entering `pending` meets the partial
  unique index, and a collision answers `409 publicExists`. A job in `pending`, `writing`, `published`, `cancelled` or
  `budgetSpent` answers `409 notRetryable`: the job's state alone decides it, never the item's recipe id; that condition holds for every "Try again" edge above. Attempts carry over a retry, and a retry spends no allowance unit. On the import path attempts are counted on the import item (`recipe_import_items.public_attempts`, below), so a new job on the same item reads the item's count and Start answers `409 attemptsUsed` at 3. Lead default, owner may revise.
- `failed` rests like `checkRefused`: it keeps `facts_snapshot`, `source_steps` and `output` while attempts < 3, can be
  retried or cancelled, expires to `cancelled` after 24 hours, and is final at 3 attempts. The cancel route accepts
  every state in the transition list above, and clears the snapshots in the same UPDATE.
- The claim is one conditional UPDATE: state `pending`, or state `writing` with `claimed_at` older than the visibility
  timeout, and in both cases `state_changed_at > now() - 10 min`. Only a claim from `pending` adds an attempt, on the owner of the count, and every claim adds one to the owner's `public_writer_calls`. The result write needs `state = 'writing'` and `claimed_at` equal to the claim it holds, plus the same age test. Every write route runs the shared expiry function under the job lock first. A transport failure is not acked, so the message returns and the
  re-claim `writing` to `writing` spends no attempt and leaves `state_changed_at` alone, so the 10-minute window is not
  extended.
- After `privateCopyChanged` the re-entry rebuilds `facts_snapshot`, `source_steps` and `private_digest` from the changed private copy.
- A Publish that answers `503 checkUnavailable` leaves the job `ready` and spends no attempt.
- A job is **final** in exactly one of these cases: `published`, `cancelled`, `budgetSpent`, `failed` at 3 attempts, and `checkRefused` at 3 attempts. `ready` is never final. The explicit list is the rule, here and everywhere a final state clears the job's text. `finished_at` is set with `COALESCE(finished_at, now())` on entering a final state and is never moved after. The cancel and keepPrivate edges out of a final state (`failed` or `checkRefused` at 3 attempts, `budgetSpent`) are housekeeping and keep `finished_at`.
- `facts_snapshot`, `source_steps` and `output` are cleared only on entering a final state, and on cancel. They are kept while "Write it
  again" or "Try again" can still happen. While the sweep runs, the job's text is cleared at most 73 h 15 min after Start (above).
- The item's draft is `recipe_import_items.payload`, everywhere in this feature. Only `claimSave`, called by Publish or keepPrivate on the public-only path, clears it (migration 0059 allows no other clear). Nothing else sets it to NULL: the worker never writes it, the expiry and the sweep never touch it (after the sweep `payload` is NOT NULL and the item's stage is unchanged), and an explicit discard removes it by deleting the whole import. It otherwise lives under ADR-0072's 30-day purge (FR-033).
- Publish on the public-only path (the job has an import item and no private copy) calls `claimSave` with the public recipe's id, under the import header lock, using the `decision_rev` it read under that lock. That records the recipe id and `saved_at` on the item and clears the item's draft, so a published import is no longer listed and reopens the recipe even after its job row is deleted (FR-044a). `claimSave` needs the item's `matched_at` and `statement_kind`. Publish and keepPrivate require `stage = 'matched'` under the item lock before the recipe insert, and otherwise answer `409 { code: 'itemNotReady' }`, retryable, with nothing written. An `ImportItemChangedError` from `claimSave` rolls the transaction back and maps to the same `409 itemNotReady`. Start answers `409 itemNotReady` for an unmatched item. A reopening `upsertItems` cancels the item's live job in the same transaction (header, then item, then job). On the Both path Publish does not write the item: Start already saved it, and `recipe_idx` is unique.
- keepPrivate (`POST /api/v1/public-version-jobs/{jobId}/keepPrivate`) applies to the public-only path only (`import_item_import_id` set, `private_recipe_id` NULL). The checks run in this order, and none infers a state from the item's recipe id: (1) a job that is not public-only, or has no item (an explicit discard deleted it), answers `409 notKeepable`; (2) a `published` job answers `409 notKeepable`; (3) an item with `saved_at` set answers `200 { recipeId }` with the item's recipe id, or `409 notKeepable` when that recipe id is NULL; (4) a `cancelled` job answers `409 notKeepable`; (5) an item that is not matched answers `409 itemNotReady`, after the `cancelled` check so a replay still wins. Otherwise one transaction: the lock order below, the unit charge, `claimSave` of the item's draft as a private recipe, and the job moved to `cancelled` from `pending`, `writing`, `ready`, `checkRefused`, `failed` or `budgetSpent`, with `source_steps`, `facts_snapshot` and `output` set to NULL. A refusal by `admit` rolls everything back (`429 IMPORT_QUOTA_EXCEEDED`), and so does no free slot (`403 PRIVATE_SLOTS_FULL`, nothing charged). A `budgetSpent` job answers `201`, ends `cancelled` and spends one unit.
- Cancel moves every state except `published` to `cancelled`, `budgetSpent` included. On the public-only path the cancel route is an explicit discard: after it ends the job it calls `ImportService.delete` in its own transaction (no evidence row and no source-record row references `recipe_import_items` or the import header with `ON DELETE CASCADE`, so the delete never removes one), so the header, the items and the lines go (the lines and items cascade) and the job's item pair goes to NULL. A job with no item then answers keepPrivate `409 notKeepable` and charges nothing. The expiry and the sweep are not a discard: they leave the import and its draft in place.
- Start, and the choice page's private Save, cancel the item's live job in the same transaction as their own work, except that a Start with the same choice as the live job returns that job and cancels nothing (this applies on the public-only path: a Both Start saves the item, so a repeat Both Start answers `itemSaved`, and P6 reaches the live Both job through the recipe's `publicVersionJob`). A Start with a changed choice cancels the live job and starts a new one in the same transaction. Attempts carry over, because the item holds the count. Start on an item whose `saved_at` is set answers `409 { code: 'itemSaved', recipeId }` for either choice, and the client opens the recipe (P6). Start checks, in order: `itemSaved`, `notPasteItem` (a `bulk` item never starts a public version), `attemptsUsed`, `itemNotReady`, the needs refusal (no statement), `publicExists`, `offerChanged`.
- Lock order for every paste and job transaction: the import header, then the item, then the allowance, then the DD33 recipe-limit lock, then the job (ADR-0073's allowance-before-DD33 order, and the header-first order of import advance). Every writer that touches both the item and the job locks the item and then the job: the worker claim, the result write, the lazy expiry inside reads and writes, and the sweep (`FOR UPDATE SKIP LOCKED` on both). The bulk save takes DD33 and then its header, so a deadlock cycle with a paste transaction is possible: the paste routes retry once on `40P01`, and a follow-up task makes the bulk save lock its header before its recipe write (T314).
- Every pair of states that this list does not name is refused.

## Columns on existing tables

- `recipes.public_credit text NULL`: the credit a public version carries, set in the Publish transaction from the
  credit the cook was shown and the server compared (FR-035). CHECK in (`free`, `paid`), and CHECK `public_credit IS
NOT NULL` if and only if `source_type = 'commise_written'`. Both are `NOT VALID` then `VALIDATE` (expand-only). The
  display reads this column: `free` shows `credit.basedOn` with the site read through `source_record_id` to the
  record's `source_key`, and `paid` reads no site (FR-060, FR-018). One-way door, named in the feature ADR, owed (T004).
- `recipes.source_record_id uuid NULL` and `recipes.source_page_key text NULL`: mark a public version. FK
  `recipe_source_records`, no cascade. A partial `UNIQUE (source_page_key) WHERE source_page_key IS NOT NULL` gives one
  public version per source page (FR-034) and is Publish's idempotency key. The key is released (set to NULL) in the same
  transaction as its cause: delete (the row goes), a 020 rejection, or a publisher opt-out
  (FR-034a).
- Provenance: a public version has `source_type = 'commise_written'`, no `source_kind` and no `statement_kind`. The
  existing `source_type` CHECKs gain the value. `public_web` + `imported_public` is wrong, because it reads as a web
  copy. One-way door, named in the feature ADR, owed (T004).
- The rights label "Steps written by Commise" (016-FR-015c) and the licence `cc-by-sa-4.0` are derived from
  `source_type` in `recipe-core` (`rightsLabelOf`, `licenceOf`). There is no column for either.
- There is no discard column. An explicit discard on the public-only path deletes the import through `ImportService.delete` in its own transaction (above), so a discarded import is not listed because it no longer exists. The list of unfinished imports excludes an item whose `saved_at` is set, and a recipe id on the item wins over everything (FR-044a). The reopen checks `saved_at` first, then the latest job's state.
- Import item `public_attempts smallint NOT NULL DEFAULT 0 CHECK (public_attempts BETWEEN 0 AND 3)`: the writer attempts
  made for this item across all of its jobs (C-7). A column and not a sum over the jobs, because finished jobs are deleted
  after 7 days and an item lives up to 30. On the import path the item is the only holder of the count: the claim UPDATE adds one here and never writes the job's own `attempts`, and a new job reads the item's count. It is independent of the job partial unique index, which
  still allows one live job per page. The writers are the worker's claim and the expiry of a `pending` job (every expiry from `pending` counts one, above). Lead default, owner may revise.
- Import item `public_writer_calls integer NOT NULL DEFAULT 0` and `public_writer_cost_micro_usd bigint NOT NULL DEFAULT 0`: the AI-use counters of FR-086 for the import path, held on the item by the same rule as the attempts (the job holds them on the later route). Calls add one on each claim, a re-claim included. Cost is added at the budget settle (DD21). Parses are already counted by the item's `parse_generation`. These are persisted columns, so they go in the feature ADR (T004).
- Import item `choice text NULL CHECK in ('private','public','both')`. Not a new `visibility` value, which
  `importSchemaParity` pins.
- Allowance: a paste spends its one unit only at save, in the transaction of whichever save ends it in a recipe (keepPrivate, Publish, the import pipeline's private save, or the Both path's private save in Start), guarded by
  `recipe_import_items.allowance_spent_at` (FR-016a), and charged under the scope that the item's `channel` names (below), never a fixed paste scope. Making a public version spends no unit of its own, on the import
  path or on the later route (`POST /api/v1/recipes/{recipeId}/public-version`). Cancel, expiry and the sweep spend
  nothing. `import_allowance_events` and its channel CHECK are unchanged.
- Item channel: `recipe_import_items.channel text NOT NULL DEFAULT 'bulk' CHECK (channel IN ('bulk', 'paste'))` (the 0059 convention for a text column with a CHECK), and `CHECK (channel = 'bulk' OR ordinal = 0)`, so a paste item is always the only item of its import. A file import creates `bulk` items, which pay when their lines are sent. A pasted recipe, a pasted link and a share-button import each create one `paste` item, one recipe per import, and a paste item spends its one unit only when the import ends in a saved recipe. The create path refuses `paste` unless the import's `expectedTotal` is 1. The DAL writes `channel` on insert only, and a BEFORE UPDATE trigger refuses any change of it, in either direction, with `IS DISTINCT FROM` (T213, T215). Every existing item reads `bulk`. A constant default makes the add cheap and expand-only (ADR-0035). The charge scope comes from this column.
- Check relaxed: `recipe_import_items_job_needs_payment` (`parse_job_id IS NULL OR allowance_spent_at IS NOT NULL`, migration 0059) becomes `parse_job_id IS NULL OR allowance_spent_at IS NOT NULL OR channel = 'paste'`. It is relaxed for paste items only, because a paste's extraction no longer pays and its parse job exists before the unit is spent. A bulk item still pays when its lines are sent, so the CHECK keeps holding for it. `NOT VALID` then `VALIDATE` (ADR-0035). The migration follows the 0076 and 0077 twin pattern: the first sets `SET LOCAL lock_timeout = '5s'` and drops and re-adds the CHECK `NOT VALID` in one transaction, and the `_validate` twin runs the `VALIDATE`.
- Recipe read, owner only: `hasSourceRecord` (boolean, no column). True when a `recipe_source_records` row exists
  whose `evidence_id` equals this recipe's evidence row (several rows: the latest `recorded_at`, which the later route
  uses). Only an import writes a source record. An edit in the editor never does. Omitted for any other viewer.
- Monitoring counts public versions per `source_key` from `recipes.source_page_key` and the source records, for the
  rate alarm only. There is no per-source ledger and there are no caps (owner ruling 2026-11-15).
- Publish confirmation: one row in `recipe_statement_attestations` (ADR-0095, PR #301, not merged): mode implicit, choice `publicConfirm`, action `create`, wording `publicVersionConfirm.v1`. Licence acceptance (FR-062) is that confirmation.

## Identity

Identity's database gains the `age_assurances` table now, as defined in `specs/016-legal-compliance-framework/data-model.md` §3 (FR-016, FR-016b). This feature writes `basis = self_attested`, `floor_met = 16`, `wording_version = ageConfirm.v1` and the cook's `locale`. Account erasure
deletes the row, and the erasure coverage test covers it. The Clerk claim `public_metadata.ageFloorMet` (the integer `16`) is set after the
row is written. Recipe-service holds no age data. `clerk-verify` parses the claim into the `Principal` field `publishAgeMet`.

## Source evidence retained

ADR-0089 §6's evidence record holds no source steps. This feature keeps source step text in `public_version_jobs.source_steps`, while the job lives (at most 73 h 15 min, above), so a retry sends the writer the same text, and in the import item's draft until FR-033 clears it. The source record keeps hashes only. Keys are never
deleted, so a missing key version is an operator fault. A later save then answers `503 checkUnavailable` and raises an
alarm, and Publish answers the same `503`, leaving the job `ready` (FR-050a).

## Not stored

The source steps and title text, once the job has ended (`source_steps` is NULL at every final state and on cancel). The prompt. The model's raw answer. The writer's queue message holds the job id only, never step text. Logs carry outcome and refusal category only.

## AI-use metric (no table)

The writer's calls and their cost are measured per import and per job, and no per-cook read cap or new allowance channel exists (owner ruling 2026-11-19). The metric is emitted, not stored: `PublicVersionAiUse` carries the dimension `Stage` (ADR-0062, DD29) and `outcome`, one of `savedPrivate`, `published`, `both` or `notSaved`, with the call count and the cost of the import's jobs. It is emitted once, when the outcome is final, and only if the owner's `public_writer_calls` is above 0; it reports the item's `parse_generation` too. The points are: (1) import path, saved: when the item is saved and has no live or resting job left (keepPrivate, a public-only Publish, a Just-for-me save after the job expired, or the Both job reaching a final state): `savedPrivate`, `published` or `both`. (2) Import path, removed unsaved: a discard, or the 30-day purge of an item with `saved_at` NULL: `notSaved`. (3) Later route: when its job reaches a final state: `both` or `savedPrivate`. It is never emitted at Start's private save, at a cancel that replaces a live job (a Start with a changed choice, the choice page's private Save, a reopening `upsertItems`), or at an expiry alone. A cook's own exit from a Both job ends the job in a final state, so it emits `savedPrivate`, and a Publish emits `both`. FR-086 states the requirement and the accepted risk it watches.
