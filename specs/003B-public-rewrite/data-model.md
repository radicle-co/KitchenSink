# Data Model: Public Versions of Imported Recipes

Recipe database. One migration plus its `_validate` twin (next free numbers at build time). Expand-only (ADR-0035).
Owner, migrator and service roles per ADR-0039. Every one-way door below goes in the feature ADR before code.

## `recipe_source_records` (append-only, never shown)

One row per third-party import item (the page is `page_key`), written in the same transaction as the item's save or the job's creation. It is
the source of truth for this feature (FR-080). It extends ADR-0089 §6's evidence by reference and does not cascade from
a recipe, so it outlives the private copy and the public version (C-14). It holds no cook id: the job and the public version carry the
owner, and neither the fingerprint nor the monitoring count needs the cook. So erasure has nothing to sweep here, and the table goes
in `erasureSweepCoverage`'s `RETAINED_BY_RULING` map with this reason.

The job has no `attempts` column. The attempt count (C-7) belongs to a **holder** chosen by `path`: for `public` the import item holds it (`recipe_import_items.public_attempts`), and for `both` and `later` the private recipe holds it (`recipes.public_attempts`), both below. Every claim from `pending` and every expiry from `pending` adds one to the holder, in the same UPDATE. The job read answers `attempts` from its holder. A job with no holder (its private copy was deleted, or its import was discarded) counts nothing and has no attempts to read.

Indexes:

- `UNIQUE (page_key) WHERE state IN ('pending','writing','ready')`: one live job per source page. A second cook who collides is told there is a version on its way (`publicExists.writing`) and keeps Private. A job re-entering `pending` meets the same index, and a collision there answers `409 publicExists`.
- `(user_id, created_at)`: the erasure sweep and the test-principal purge are user-keyed and find a cook's job rows through it. Routes read one job at a time. Only the promoter's seat count reads the `pending` and `writing` jobs of every cook, by `state` (Rest-public, below), which the partial unique `page_key` index above covers.
- `(private_recipe_id, created_at DESC)`: the owner-only `publicVersionJob` field of `GET /api/v1/recipes/{id}` only (no list read carries it), the later route's latest-job read, and the `ON DELETE SET NULL` foreign key.
- `(import_item_import_id, import_item_ordinal, created_at DESC)`: the import item view's latest job, and the `ON DELETE SET NULL` when an import is deleted.

The job points at its import item by the composite key: `FOREIGN KEY (import_item_import_id, import_item_ordinal) REFERENCES recipe_import_items(import_id, ordinal) ON DELETE SET NULL`, and `CHECK (num_nonnulls(import_item_import_id, import_item_ordinal) IN (0, 2))`, so the pair is both set or both NULL. Deleting an import (an explicit discard on the public-only path, below) deletes its header, its items and its lines by cascade, and the job's pair goes to NULL, so the job then has no item. No evidence row and no source-record row references the import item or the import header with `ON DELETE CASCADE`, so a discard never removes them.

Every expiry counts from `state_changed_at`, so a retry starts a fresh window. A job expires lazily, in the data layer, in the same transaction before an insert and again on every read: a job in
`pending` or `writing` for more than 10 minutes becomes `failed`. Every expiry from `pending` counts one attempt on the holder (the item's `public_attempts` for path `public`, the recipe's `public_attempts` for `both` and `later`), in the same UPDATE: `pending` is by definition unclaimed since it was entered, so there is no `claimed_at` test, and a retry loop that never reaches a worker, with the queue down, ends at 3. A job in `ready` for more than 24 hours becomes
`cancelled`, and so is a `checkRefused` or `failed` job after 24 hours, resting (fewer than 3 attempts) or final (3 attempts). A sweep on the band drain's existing 15-minute tick (`bandDrain.ts` in recipe-workers, beside `purgeFinishedImports` and the parse-job sweep) runs the same expiry function the reads use, and clears only the job's own text (`source_steps`, `facts_snapshot`, `output`) as it ends the job. It never touches the import item's draft, `recipe_import_items.payload`, which stays until `claimSave` clears it (every save that ends the paste in a recipe, FR-016a), or until ADR-0072's 30-day purge removes it (FR-033). The sweep follows the lock order below: it locks the holder (the item or the recipe, by `path`) `FOR UPDATE SKIP LOCKED`, then the job `FOR UPDATE SKIP LOCKED`, and re-checks the expiry under the lock. The lazy expiry inside reads and writes follows the same order: it reads the job's `path` and holder key unlocked (the path never changes, and a key changes only to NULL), then locks the holder and then the job. The sweep runs before the purge on each tick, and each job it or the lazy expiry ends calls `promote()` after commit (Rest-public). It follows ADR-0072's purge rules: its own transaction, `FOR UPDATE SKIP LOCKED`, and it runs even if an earlier sweep failed. Every tick publishes the age of the oldest expired job with `Stage` (ADR-0062), and a behind alarm, `PublicVersionJobSweepBehindAlarm`, is styled like `BulkImportPurgeBehindAlarm`. It adds no Lambda, no schedule rule and no NAT consumer. So a job nobody reads cannot hold its page key or its text: while the sweep runs, the job's text is cleared at most 73 h 15 min after Start, which is 3 x (20 min + 24 h) + 15 min: 3 attempts, each at most 20 minutes of work and 24 hours of rest, and one 15-minute sweep tick (FR-033). A sweep that runs late fires `PublicVersionJobSweepBehindAlarm`. A swept or expired import stays in To review in My recipes as an ordinary unfinished import (FR-044a).

Finished jobs are deleted 7 days after `finished_at` by the existing retention sweeper. The table is user-keyed: add it
to `erasureSweepCoverage` and to the test-principal purge.

## State transitions (job)

```text
pending ──claimed by worker──────────────▶ writing         (one attempt on the holder, one writer call)
writing ──re-claim after a transport failure──▶ writing    (no attempt spent, state_changed_at unchanged, claimed_at updated, only while state_changed_at is within 10 minutes)
writing ──engine ok──────────────────────▶ ready           (output stored, reservation settled)
writing ──check refused, attempts < 2────▶ pending         (automatic retry)
writing ──check refused, attempts >= 2───▶ checkRefused    (rests while attempts < 3, final at 3)
writing ──ceiling denial─────────────────▶ budgetSpent     (refund, ack, never redelivered)
pending|writing ──10 min / maxReceive────▶ failed          (rests while attempts < 3, final at 3; every expiry from pending counts an attempt)
ready ──Publish (server re-checks pass)──▶ published       (same transaction as the recipe insert)
ready ──24 h─────────────────────────────▶ cancelled
ready ──"Write it again" (422 flags, 422 tooSimilar, 409 privateCopyChanged)──▶ pending   (attempts < 3)
checkRefused ──"Try again"───────────────▶ pending         (attempts < 3)
checkRefused ──24 h (attempts < 3)───────▶ cancelled
failed ──"Try again"────────────────────▶ pending         (attempts < 3)
failed ──24 h (attempts < 3)─────────────▶ cancelled
checkRefused|failed ──24 h (attempts = 3)────▶ cancelled        (the job's own text is already cleared)
[promoter] ──inserts the job (rest-public)─▶ pending       (no attempt spent; the job's windows start here)
pending|writing|ready|checkRefused|failed|budgetSpent ──cancel (on a saved item, the Both path and the later route: Stop, Back from the writing screen or from the review, review.notNowBoth, failed.done and the blocked and final exits; a Start that starts a new job (including the later route's Start, which cancels the recipe's resting job) and a reopening `upsertItems` also cancel, replacing the job, and the choice page's private Save cancels it as part of the save; on the public-only path of a paste item: Stop and review.discard, where the import is also deleted, and Back from the review calls no route; on a file item: review.discardFile calls `discardItem`, which cancels the job and deletes nothing)──▶ cancelled   (a late result is dropped: the result write needs state `writing` and the claim that wrote it, below)
pending|writing|ready|checkRefused|failed|budgetSpent ──keepPrivate (path `public` only; on a file item it answers 202 and the bulk save runs, R2)──▶ cancelled   (published answers 409 notKeepable)
```

Rules:

- The retry route (`POST /api/v1/public-version-jobs/{jobId}/retry`) makes `ready`, `checkRefused` and `failed` to
  `pending`. It answers `409 attemptsUsed` at 3 attempts on the holder, and `409 notRetryable` for a job with no holder (a `both` job whose copy was deleted). Re-entering `pending` meets the partial
  unique index, and a collision answers `409 publicExists`. A job in `pending`, `writing`, `published`, `cancelled` or
  `budgetSpent` answers `409 notRetryable`: the job's state alone decides it, never the item's recipe id; that condition holds for every "Try again" edge above. A retry spends no allowance unit. The attempt count belongs to the holder named by `path` and nobody else: the item for `public`, the private recipe for `both` and `later`. A new job reads it from there, so reopening an import or starting a new job does not reset it. Editing the private copy never resets `recipes.public_attempts` either: it is 3 per recipe in total.
- `failed` rests like `checkRefused`: it keeps `facts_snapshot`, `source_steps` and `output` while attempts < 3, can be
  retried or cancelled, expires to `cancelled` after 24 hours, and is final at 3 attempts. The cancel route accepts
  every state in the transition list above, and clears the snapshots in the same UPDATE.
- The claim runs under the holder lock and then the job lock (holder-then-job), and tests the job row: state `pending`, or state `writing` with `claimed_at` older than the visibility
  timeout, and in both cases `state_changed_at > now() - 10 min`. Only a claim from `pending` adds an attempt, on the holder, and every claim adds one to the `public_writer_calls` of the counter owner (the item when the job has an import item, the job when it has none). The result write needs `state = 'writing'` and `claimed_at` equal to the claim it holds, plus the same age test. Every write route runs the shared expiry function under the job lock first. A transport failure is not acked, so the message returns and the
  re-claim `writing` to `writing` spends no attempt and leaves `state_changed_at` alone, so the 10-minute window is not
  extended.
- After `privateCopyChanged` the re-entry rebuilds `facts_snapshot`, `source_steps` and `private_digest` from the changed private copy.
- A Publish that answers `503 checkUnavailable` leaves the job `ready` and spends no attempt.
- A job is **final** in exactly one of these cases: `published`, `cancelled`, `budgetSpent`, `failed` at 3 attempts, and `checkRefused` at 3 attempts. `ready` is never final. The explicit list is the rule, here and everywhere a final state clears the job's text. `finished_at` is set with `COALESCE(finished_at, now())` on entering a final state and is never moved after. The cancel and keepPrivate edges out of a final state (`failed` or `checkRefused` at 3 attempts, `budgetSpent`) are housekeeping and keep `finished_at`.
- `facts_snapshot`, `source_steps` and `output` are cleared only on entering a final state, and on cancel. They are kept while "Write it
  again" or "Try again" can still happen. While the sweep runs, the job's text is cleared at most 73 h 15 min after Start (above).
- The item's draft is `recipe_import_items.payload`, everywhere in this feature. Only `claimSave` clears it (migration 0059 allows no other clear): every save that ends the paste in a recipe (FR-016a). Nothing else sets it to NULL: the worker never writes it, the expiry and the sweep never touch it (after the sweep `payload` is NOT NULL and the item's stage is unchanged), and a paste item's explicit discard removes it by deleting the whole import (a discarded file item keeps its draft until ADR-0072's purge). It otherwise lives under ADR-0072's 30-day purge (FR-033).
- Publish on the public-only path (the job's `path` is `public`) calls `claimSave` with the public recipe's id, under the import header lock, using the `decision_rev` it read under that lock. That records the recipe id and `saved_at` on the item and clears the item's draft, so a published import is no longer listed and reopens the recipe even after its job row is deleted (FR-044a). `claimSave` needs the item's `matched_at` and `statement_kind`. Publish and keepPrivate require `stage = 'matched'` under the item lock before the recipe insert, and otherwise answer `409 { code: 'itemNotReady' }`, retryable, with nothing written. An `ImportItemChangedError` from `claimSave` rolls the transaction back and maps to the same `409 itemNotReady`. Start answers `409 itemNotReady` for an unmatched item. A reopening `upsertItems` cancels the item's live or resting job in the same transaction (header, then item, then job). On the Both path Publish does not write the item: Start already saved it, and `recipe_idx` is unique. On the `both` and `later` paths Publish locks the private recipe before the job, and a `both` job whose copy was deleted publishes without the `privateCopyChanged` digest check (there is no copy to compare).
- keepPrivate (`POST /api/v1/public-version-jobs/{jobId}/keepPrivate`) applies to path `public` only, read from the job's `path` and never from `private_recipe_id`. The checks run in this order, and none infers a state from the item's recipe id: (1) a job whose `path` is not `public` (a `both` job whose copy was deleted included), or that has no item (an explicit discard deleted it), answers `409 notKeepable`; (2) a `published` job answers `409 notKeepable`; (3) an item with `saved_at` set answers `200 { recipeId }` with the item's recipe id, or `409 notKeepable` when that recipe id is NULL; (4) a `cancelled` job answers `409 notKeepable`; (5) an item that is not matched answers `409 itemNotReady`, after the `cancelled` check so a replay still wins. Otherwise one transaction: the lock order below, the unit charge, `claimSave` of the item's draft as a private recipe, and the job moved to `cancelled` from `pending`, `writing`, `ready`, `checkRefused`, `failed` or `budgetSpent`, with `source_steps`, `facts_snapshot` and `output` set to NULL. A refusal by `admit` rolls everything back (`429 IMPORT_QUOTA_EXCEEDED`), and so does no free slot (`403 PRIVATE_SLOTS_FULL`, nothing charged). A `budgetSpent` job answers `201`, ends `cancelled` and spends one unit. On a file (`bulk`) item keepPrivate runs checks (1) to (5) and then, in one transaction, cancels the job and writes `choice = 'private'`, and answers `202 { importId, ordinal }`: the client calls advance, and the bulk save saves the recipe with its holds, its binding mode and DD33. It charges nothing, because a file item is paid before any job exists. With no free slot it answers `403 PRIVATE_SLOTS_FULL`.
- Cancel moves every state except `published` to `cancelled`, `budgetSpent` included. On the public-only path of a paste item the cancel route is an explicit discard: after it ends the job it calls `ImportService.delete` in its own transaction (no evidence row and no source-record row references `recipe_import_items` or the import header with `ON DELETE CASCADE`, so the delete never removes one), so the header, the items and the lines go (the lines and items cascade) and the job's item pair goes to NULL. A job with no item then answers keepPrivate `409 notKeepable` and charges nothing. Cancel on an already-cancelled public-only job is idempotent: if the item pair is still set it runs `ImportService.delete` again and answers as the first call did, and if the pair is NULL it does nothing and answers `200`. A discard with no job uses the existing import delete, `DELETE /api/v1/import/{importId}`, for a paste item. On a file item cancel only ends the job and deletes nothing: the explicit discard of a file item is `discardItem` (below). The expiry and the sweep are not a discard: they leave the import and its draft in place.
- A Start with the same choice as a live job (`pending`, `writing` or `ready`) returns that job and checks nothing else, once the item is known to be unsaved (this applies on the public-only path: a Both Start saves the item, so a repeat Both Start answers `itemSaved`, and P6 reaches the live Both job through the recipe's `publicVersionJob`). A Start that starts a new job (a changed choice, or a same-choice Start that found only a resting job), the choice page's private Save, the review wizard's per-recipe `choice = 'private'` write on a file item and a reopening `upsertItems` cancel the item's live or resting job in the same transaction as their own work. A resting job (`checkRefused` or `failed` below 3 attempts) is never left behind, so no job of the item holds step text after a save or a Publish. Start on the later route locks the recipe row `FOR NO KEY UPDATE` before it reads the recipe's latest job (by `private_recipe_id`, a Both job included). When that job is `pending`, `writing` or `ready` it returns it with `202` and checks nothing else, so a second device of the same cook gets the same job (FR-034) and no row is inserted. When that job is resting (`checkRefused` or `failed` below 3 attempts), Start cancels it in the same transaction, clearing its text, and then answers `409 attemptsUsed` when `recipes.public_attempts` is 3, checked after the live-job return. A Both Start on an item at 3 attempts answers `attemptsUsed` before it saves anything, and every save of an item into a private recipe (the Both Start's save, keepPrivate, the bulk save) copies `item.public_attempts` into `recipes.public_attempts` in the same transaction. Start on an item whose `saved_at` is set answers `409 { code: 'itemSaved', recipeId }` for either choice, and the client opens the recipe (P6). Start on a discarded file item answers `404`, as for a missing item. Start checks, in order: `itemSaved`, the live job with the same choice (returned at once), `attemptsUsed`, `itemNotReady` (an unmatched item, or a file item whose unit is unpaid), the needs refusal (no statement), `publicExists`, `offerChanged`.
- Lock order for every paste and job transaction: the import header, then the item, then the allowance, then the DD33 recipe-limit lock, then the private recipe row, then the job (ADR-0073's allowance-before-DD33 order, and the header-first order of import advance). Every writer that touches both a holder and the job locks the holder and then the job: the worker claim, the result write, the lazy expiry inside reads and writes (the job read and retry included) and the sweep (`FOR UPDATE SKIP LOCKED` on both). The holder is the item for path `public` and the recipe for `both` and `later`. The writer reads the job's `path` and holder key unlocked first, which is safe because the path never changes and a key changes only to NULL. The later route's Start locks the recipe `FOR NO KEY UPDATE` before it reads the latest job, and a Publish on `both` and `later` locks the private recipe before the job. Recipe edit, save and delete cannot deadlock with this: they take DD33 and then the recipe, and a delete locks the recipe and then the job through `ON DELETE SET NULL`. The bulk save takes the header (`FOR NO KEY UPDATE`) and then the item (`FOR UPDATE`) first, through `ImportedCreate.beforeLocks(tx)`, which `recipes.service.ts` runs as the first statement of its transaction, then DD33, the recipe insert, and `afterWrite` and `claimSave` (whose header re-lock is a no-op). So the bulk save and a paste transaction take one order, and there is no deadlock to retry (T314). Every route on the import path locks the header, then the item `FOR UPDATE`, then the job, and the later route locks the recipe `FOR NO KEY UPDATE`, then the job. The rest-public route locks the header and then the items in ordinal order. The promoter takes one global advisory lock first (no route takes it, so it forms no cycle with the route order), then the header `FOR KEY SHARE SKIP LOCKED`, then the item `FOR UPDATE SKIP LOCKED`, then the job (Rest-public, below).
- The purge skips at the header (M2). ADR-0072's 30-day purge adds `AND NOT EXISTS` (a job of this import in `pending`, `writing`, `ready`, or `checkRefused` or `failed` below 3 attempts, or an item with `public_requested_at` set and younger than 30 days, which is a ticked row still waiting for its job, so a stuck marker ages out with the import) to its header subquery and keeps `FOR UPDATE SKIP LOCKED` on the header. The tick runs the job sweep before the purge. On the import path Start, retry, Publish, keepPrivate, cancel, `discardItem` and the rest-public route hold the header lock and set `recipe_imports.updated_at = now()`, so a job started on day 29 restarts the 30-day clock. If the purge locks the header first, Start waits and then answers `404`.
- Discarding a file item (R1): file items never delete an item row, because ordinals stay contiguous (migration 0059) and a re-sent chunk would re-upsert a deleted one. `discardItem(importId, ordinal)` runs under the header lock, cancels the item's job and moves the cursor like a skip. A discarded item is left out of the advance save, of Start, of the unfinished counts and of rest-public, and `upsertItems` refuses it as locked. Ordinals and `expected_total` do not change. The paste path still deletes the whole import. A discard spends no unit and none is refunded: a file item is already paid.
- Advance never saves an item whose `choice` is `public` or `both`. Every private save of a file item goes through the bulk save: while a keepable job exists, keepPrivate cancels it and writes `choice = 'private'` in one transaction; with no keepable job (`cancelled`, or none), and always after Start's `409 attemptsUsed` whatever the job's state, the wizard's per-recipe decision write sets `choice = 'private'` and cancels any live or resting job in the same transaction; either way the client then calls advance (R2), and Start's `409` writes nothing. The Both Start's private save on a file item goes through the same bulk save.
- Every pair of states that this list does not name is refused.

## Rest-public (file imports)

"Make the rest public" after a file import asks for the public version of every ticked third-party recipe. The jobs start as writer capacity frees up (below), and the cook still reads and confirms each draft. An "I wrote this" item goes public through its visibility and never through `choice`: the route writes ADR-0072's `visibility = 'public'` on an item whose `statement_kind = 'authored'` and leaves `choice` NULL, and the advance saves it as today. The route is `POST /api/v1/import/{importId}/rest-public` (the contract). It runs in one transaction under the header lock, with the items `FOR UPDATE` in ordinal order, and writes no job. Each eligible third-party item gets `choice = 'public'` and `public_requested_at`. Eligible means unsaved, not discarded, no job at all, and an offer of `choice` or `publicOnly`. A row whose current offer differs from the `shownOffer` it sent is not marked and answers `skipped` with `offerChanged` (checked after `publicExists`, the order of Start).

**Marker rule (stated once, every other section points here).** `public_requested_at` is set only by the rest-public route. It is cleared in the same transaction as every job creation (a hand Start and the promoter's insert), every private save (keepPrivate, the bulk save and the Both Start's save), every choice write (the review wizard's per-recipe decision), `discardItem` and a reopening `upsertItems`. Before each insert the promoter re-checks the item: the current offer (which re-reads `aiOptOut`, `publisherOptOut` and the switch), unsaved, not discarded, `choice = 'public'`, and attempts below 3. When a re-check fails or the insert is lost, an unmatched or unpaid item keeps its marker and reads `waiting`, and every other failure clears it (a lost page-key insert, no free slot, a spent budget, a changed offer or choice). A marker that is never served ends with the 30-day purge.

**The promoter** is `promote()`: global (it takes no `userId`), in `@kitchensink/recipe-core` under the subpath `./public-version/promoter` (`RC/publicVersion/promoter.ts`), with its SQL behind an injected runner (the precedent is `resolution/bandAuthorityStore.ts`), so recipe-service and recipe-workers call the same code. It is a loop of one-item transactions (lock, pick one item, insert one job, commit), so no two unique-key inserts are ever held together. Each transaction: (1) `pg_advisory_xact_lock(<the fixed bigint 'pvFanOut'>)`; (2) count every job in `pending` or `writing` across all cooks and paths, and stop when the count has reached `PUBLIC_VERSION_FANOUT_SEATS`; (3) pick the next item: each free seat goes to the oldest marker of the cook with the fewest live jobs (`pending` or `writing`); (4) lock the header `FOR KEY SHARE SKIP LOCKED` (so it never inserts a job into an import the purge holds, and the purge's `FOR UPDATE SKIP LOCKED` skips a header the promoter holds; a skipped header leaves its markers for the next call, and the promoter sets no `updated_at`), then the item `FOR UPDATE SKIP LOCKED`; (5) re-check the item (marker rule); (6) insert one job (`pending`, `path = 'public'`, from the item's draft) with `ON CONFLICT (page_key) WHERE state IN ('pending','writing','ready') DO NOTHING`, clearing the marker in the same transaction; commit. The send happens after commit. A hand Start checks no seat and is never gated, but its job counts toward the total, so fan-out yields to it. The promoter takes only items that are matched and have `allowance_spent_at` set, neither matches nor binds, and dispatches work the cook confirmed (DD32). Before each insert it runs Start's budget check: when the ceiling is spent it creates nothing more for the cook and the marker rule clears that cook's markers, so those items read `privateOnly` with `budget` (`deadEnd` when no private slot is free, as at the slot pause). A lost page-key insert leaves the offer reading `publicExists` (two rows of one file that point at the same page included). A replay marks nothing that already has a job or a marker and never restarts a resting job.

**Hand-Start bound.** Hand-Start volume is human-paced. `fanOutSeats` is set under Capacity, so at `writerConcurrency` of 2 or more at least half of the writer stays free for hand Starts. At 1 fan-out can take the only seat, and a hand Start then waits inside the 10-minute pending window, which also absorbs short bursts. An attempt lost to a burst beyond that is accepted, because the cook has 3 attempts and can retry.

**Capacity.** `publicVersionCapacity(stage)` in `./public-version/writer-capacity` (`RC/publicVersion/writerCapacity.ts`) returns `{ writerConcurrency, fanOutSeats }` with `fanOutSeats = max(1, floor(writerConcurrency / 2))`, and decides prod by exact equality, as `stageClassOf` does. The infra imports it and code never imports infra: `RecipeWorkersStack` sets the writer Lambda's `reservedConcurrentExecutions` from `writerConcurrency` and injects `PUBLIC_VERSION_FANOUT_SEATS` into the band-drain and writer Lambdas, and the recipe-service stack injects the same variable. Each service's zod config reads it as an integer of at least 1, and a synth test in each stack checks it against `publicVersionCapacity` (T354). No number is written in a spec. The shared job-expiry function that every write route, read and the sweep run lives in `./public-version/job-expiry` (`RC/publicVersion/jobExpiry.ts`).

**Callers and progress.** `promote()` runs after commit, best-effort (a failure is logged and never fails the caller, and the 15-minute band-drain tick is the backstop), from the rest-public route and from every exit from `pending` or `writing`: Start's cancel (a Start that starts a new job included), keepPrivate, cancel, discard, Publish, the wizard's per-recipe private write, a reopening `upsertItems`, the worker's `writing` to `ready`, `failed`, `budgetSpent` or `checkRefused`, and both expiry paths (the lazy expiry and the sweep). A job re-entering `pending` after a refused check is not an exit. Every exit frees a seat and calls `promote()`, so each marker is promoted or cleared once the exits ahead of it in the cook-fair order have happened, and the tick promotes anything a missed call left within one tick (15 minutes). No SQS delay is used, because it would expire jobs. When a job is deleted after 7 days the tick finds no marker for it and creates nothing, because the marker was cleared when the job was created.

No job waits behind the seat limit, so every window (10 minutes, 24 hours, 73 h 15 min) counts from the job's creation, and a job never created costs no attempt. These jobs run at the slot pause (ADR-0072 section on the pause), and their exits are Publish and `discardItem`. With no free slot keepPrivate answers `403 PRIVATE_SLOTS_FULL`. The item has no extra unit to spend: Publish charges nothing for it.

Every count except `notWritten` and `expiring` is scoped to the file's third-party items the cook wants public: `channel = 'bulk'`, `discarded_at IS NULL`, a third-party source statement (not "I wrote this", which goes public through its visibility and has no job), and `choice = 'public'` (set by "Make the rest public" or by the review wizard's per-recipe For everyone). A Both item is saved privately and shows its job on its recipe's page (P6), so the grouped row does not count it (FR-088 records this call). Each count has one predicate over stored columns, and an item is counted in at most one of them (a discarded item is counted in none, and a saved item only in `published`, per its row).

**Unsaved scope (stated here only).** `notWritten` and `expiring` are the remainder: they count every unsaved, undiscarded item in the file (`saved_at IS NULL`, `discarded_at IS NULL`) that `requested`, `writing`, `ready` and `needsYou` do not hold, whatever its source statement, its choice or its place in the fan-out. That is an item never ticked, a row skipped as `offerChanged`, a third-party item with any choice, and an "I wrote this" item, including one waiting on the slot pause. So all of them read "not saved yet" (or "will be removed" at 7 days or less). The table gives the stored-column predicate. FR-087, T341 and T347 point here.

**Pause keeps the purge clock running.** The slot pause is derived from the live private-slot count and never stored (ADR-0072, the bullet "When a free cook runs out of slots, the import pauses"; ADR-0073 section 8; `importAdvance.service.ts` maps `outOfSlots` to `paused`; `privateSlots.port.ts` says the pause is derived from the live count). So the cook can act during the pause: make the rest public, skip an item, stop, free a slot by deleting a recipe or making a private one public, or move to Pro (a Pro cook never pauses for slots, ADR-0073 section 8). A skip is open for a book or paid-site item; every other item is unticked in the make-the-rest-public list. The purge clock is the import's `updated_at + 30 days`, and only a write or an `advance` moves it (`advance()` in `importAdvance.service.ts` touches it, a read does not). The pause itself neither moves nor stops it, so the clock keeps running while the import is paused unless the cook acts, and a paused item that is unsaved and undiscarded is counted in `notWritten`, or in `expiring` at 7 days or less. `yourImports.fileExpiring` warns about paused items, because the warning prompts an action the cook can take.

## Source evidence retained

ADR-0089 §6's evidence record holds no source steps. This feature keeps source step text in `public_version_jobs.source_steps`, while the job lives (at most 73 h 15 min, above), so a retry sends the writer the same text, and in the import item's draft until FR-033 clears it. The source record keeps hashes only. Keys are never
deleted, so a missing key version is an operator fault. A later save then answers `503 checkUnavailable` and raises an
alarm, and Publish answers the same `503`, leaving the job `ready` (FR-050a).

## Not stored

The source steps and title text, once the job has ended (`source_steps` is NULL at every final state and on cancel). The prompt. The model's raw answer. The writer's queue message holds the job id only, never step text. Logs carry outcome and refusal category only.

## AI-use metric (no table)

The writer's calls and their cost are measured per import and per job, and no per-cook read cap or new allowance channel exists (owner ruling 2026-11-19). The metric is emitted, not stored: `PublicVersionAiUse` carries the dimension `Stage` (ADR-0062, DD29) and `outcome`, one of `savedPrivate`, `published`, `both` or `notSaved`, with the call count and the cost of the import's jobs. It is emitted once, when the outcome is final, and only if the owner's `public_writer_calls` is above 0; it reports the item's `parse_generation` too. The points are: (1) import path, saved: when the item is saved and has no live or resting job left (keepPrivate, a public-only Publish, a Just-for-me save on the choice page, after the job expired or from the `attemptsUsed` Final screen, or the Both job reaching a final state): `savedPrivate`, `published` or `both`. (2) Import path, removed unsaved: a discard (emitted by `ImportService.delete` after commit, which both the public-only cancel and `DELETE /api/v1/import/{importId}` call, so a replay that finds the item gone emits nothing), `discardItem` on a file item whose counters are above 0 (after commit, zeroing the counters in the same UPDATE, so a second discard emits nothing), or the 30-day purge of an item with `saved_at` NULL: `notSaved`. (3) Later route: when its job reaches a final state: `both` or `savedPrivate`. It is never emitted at the Both path's private save in Start, or at a cancel that replaces a job on an unsaved import item (a Start that starts a new job, a reopening `upsertItems`). The later route's Start that cancels a resting job is that job's final state: a Both job emits `savedPrivate` by rule (1), and a later-route job emits `savedPrivate` by rule (3). The choice page's private Save is itself the outcome, so it emits `savedPrivate`. The expiry or sweep of a public-only job whose item is still unsaved does not emit, because the import remains. The 24-hour expiry of a Both or later-route job (to `cancelled`), or a 10-minute expiry that leaves it `failed` at 3 attempts, is that job's final state and emits `savedPrivate`, and so is a cook's own exit from a Both job. A 10-minute expiry below 3 attempts leaves the job resting and emits nothing. A Publish of a Both or later-route job emits `both`, and a public-only Publish emits `published`. The purge emits `notSaved` through one CTE (the victims `FOR UPDATE SKIP LOCKED`, `spent` the unsaved items with `public_writer_calls` above 0, `gone` the `DELETE ... RETURNING`, and the spent rows selected from `gone`), and the service emits after commit only, at most once; a crash between the commit and the emit loses one point, which is accepted. `ImportService.delete` uses the same shape, and a delete of an item with `saved_at` set emits nothing. For a file item whose job ends unsaved (24 hours unread, `failed` or `checkRefused` at 3, `budgetSpent`), the job's end emits `notSaved` with the item's counters and sets them to 0 in the same UPDATE, emitted after commit; a later save, discard or purge emits only if the counters are above 0 again. "Once" is tied to the write that sets `finished_at` from NULL on the job (the Both path and the later route) or to the item's save or its delete (the import path), so a second cancel of a job that is already final emits nothing. FR-086 states the requirement and the accepted risk it watches.
