# Migration Risk Matrix — Feature 005 (AI Integration)

> Scope: `0001_ai_initial` — four new tables in the new `kitchensink_ai` logical database.
> Every mitigation below is a concrete action or an executable check. "Monitor carefully" is not a
> mitigation and does not appear here.

| #    | Risk                                                                                                                                                                                       | Severity   | Mitigation                                                                                                                                                                                                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-01 | **The D-005 defect is reintroduced** — a column-level `UNIQUE` on `user_byok_keys.user_id` instead of the composite `(user_id, provider)`. Silently degrades to one BYOK key per user.     | **HIGH**   | `validation.sql` check 2b fails the migration outright. **Mutation-tested**: adding `UNIQUE (user_id)` was confirmed to raise `FAIL(2b)`. T005 asserts the same property at the unit tier, T007 at the integration tier — three independent guards.                                             |
| R-02 | **Partial migration leaves the database half-created.** A failure between table 2 and 3 yields a schema that is neither old nor new, and Drizzle would then disagree with reality.         | **HIGH**   | `forward.sql` contains no `CREATE INDEX CONCURRENTLY` and no `CREATE DATABASE`, so the entire script is transaction-safe. The runner MUST wrap it in a single `BEGIN/COMMIT` — with that, failure rolls back to an empty database and the migration is simply re-run. This is why R-06 matters. |
| R-03 | **Rollback orphans AWS Secrets Manager entries.** `user_byok_keys` holds only the ARN; `DROP TABLE` destroys the sole pointer to live third-party provider credentials.                    | **HIGH**   | `rollback.sql` blocks on a mandatory pre-step: `\copy` the ARNs to CSV, then `delete-secret --recovery-window-in-days 30` per ARN. The warning is at the top of the file, not in a runbook nobody opens. Explicitly forbids `--force-delete-without-recovery`.                                  |
| R-04 | **Rollback destroys EU AI Act provenance.** `ai_generation_records` is compliance evidence and is not reconstructible — only the SHA-256 of the sanitized prompt is stored.                | **HIGH**   | `rollback.sql` opens with an explicit destructive-loss warning naming this table first and stating why it cannot be rebuilt. Backup is a listed precondition of `forward.sql`, not only of rollback.                                                                                            |
| R-05 | **Rollback drops our grant records while agent credentials stay live.** External agents keep presenting tokens against a service that has lost its record of what was granted.             | **HIGH**   | `rollback.sql` mandatory pre-step 2: export live grants, revoke at the authorization layer **before** the DDL runs. Ordering is stated as a requirement, not a suggestion.                                                                                                                      |
| R-06 | **`CREATE DATABASE` cannot run inside a transaction**, so a runner that wraps everything in one transaction will fail on database creation if provisioning is folded into this script.     | **MEDIUM** | Scope boundary is declared in `forward.sql`'s header: database + role creation belong to the provisioning layer (CDK/DataStack + migrate Lambda), exactly as `kitchensink_recipes` does. This script assumes it is already connected to `kitchensink_ai`.                                       |
| R-07 | **`pgcrypto` is dropped during rollback**, breaking `gen_random_uuid()` for every other logical database on the shared instance — a cross-service outage caused by one service's rollback. | **MEDIUM** | `rollback.sql` explicitly does **not** drop the extension, with the reason written inline so a future editor does not "tidy it up".                                                                                                                                                             |
| R-08 | **A cross-service foreign key is added later** (e.g. `user_id → users.id`), reintroducing the local-duplication coupling the composition architecture exists to prevent.                   | **MEDIUM** | `validation.sql` check 6 asserts **zero** foreign keys on all four tables and fails if any appear. **Mutation-tested**: adding one FK was confirmed to raise `FAIL(6)`.                                                                                                                         |
| R-09 | **SQS at-least-once redelivery double-charges the user's provider account** if the idempotency guard is absent, and writes duplicate audit rows.                                           | **MEDIUM** | `UNIQUE` on both `idempotency_key` and `job_id` puts the guard in the database, not in application code. `validation.sql` check 7 fails unless **both** are present.                                                                                                                            |
| R-10 | **`prompt_templates` versioning is silently disabled** by a column-level unique on `template_key` (the previous revision declared both that and the composite — mutually contradictory).   | **LOW**    | `validation.sql` checks 3 and 3b assert the composite exists **and** the column-level one does not.                                                                                                                                                                                             |
| R-11 | **Index build blocks writes.** The standard Postgres migration hazard.                                                                                                                     | **LOW**    | Does not apply here and the reason is recorded so nobody "fixes" it into `CONCURRENTLY`: all four tables are created empty in the same run, so index builds are instantaneous with no concurrent writers. `CONCURRENTLY` would additionally break R-02's transaction safety.                    |
| R-12 | **Replication lag under backfill load.** The standard hazard for data migrations.                                                                                                          | **N/A**    | No backfill exists — there is no pre-existing data. See `migration-plan.md` → "Why there is no backfill plan".                                                                                                                                                                                  |

## Residual risk accepted

- **Rollback after production traffic is irreversibly destructive.** No mitigation makes `DROP TABLE`
  safe once rows exist; the mitigations above reduce it to "loud, ordered, and backed up". If 005 is
  live and a rollback is contemplated, the correct move is almost always a forward fix, not this
  script.
- **The pre-steps in `rollback.sql` are manual.** They are AWS-side and cross-system, so they cannot
  be enforced by Postgres. They are placed above the DDL, in a file that must be opened to be run.
