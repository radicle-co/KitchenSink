# Hazard Analysis (FMEA): Meal Planning

**Feature Branch**: `006-meal-planning`
**Created**: 2026-05-10 | **Regenerated**: 2026-08-02
**Status**: Draft
**Source**: [`v-model/system-design.md`](./system-design.md), [`v-model/architecture-design.md`](./architecture-design.md)
**Standard**: General-Purpose FMEA (non-regulated software; `domain: ''` in `v-model-config.yml`)

## Overview

FMEA for the **Meal Planning** feature. Every Phase-1 system component (`SYS-001`, `SYS-002`, `SYS-003`, `SYS-007`..
`SYS-012`) is assessed for realistic failure modes. Each hazard carries a permanent `HAZ-NNN` id linked to mitigating
`REQ-*` / `SYS-*` / `ARCH-*` identifiers, feeding Matrix H of [`traceability-matrix.md`](./traceability-matrix.md).

**Non-regulated context.** Commise meal planning is consumer SaaS. There are no life-safety, medical-device, automotive
or avionics obligations in scope. Severity is evaluated against **user trust, data integrity, privacy, availability and
platform cost**. Regulated taxonomies (ASIL, DAL, IEC 62304) are intentionally not used.

> **Regeneration note.** Hazards are **never renumbered**. Ten of the May hazards analysed components or mechanisms that
> no longer exist (a Redis cache, a USDA adapter, a premium guard, recurrence expansion, leftovers) and are marked
> **SUPERSEDED** with the reason, rather than deleted — a hazard that stops applying because the design changed is
> useful history. Nine new hazards (`HAZ-029`..`HAZ-037`) cover risks the reconciled architecture actually carries,
> several of which the May analysis could not see because it did not model the failure modes of a _degrading_ gateway.
>
> One correction is worth calling out: **HAZ-009 (stale cache) is gone because the cache is gone.** Removing a component
> removes its hazards — that is a real safety argument for the simpler design, not an accounting trick.

## ID Schema

- **Hazard ID**: `HAZ-{NNN}`, 3-digit, sequential, **never renumbered**.
- **Lineage**: mitigations cite existing `REQ-*`, `SYS-*`, `ARCH-*`, `MOD-*` ids from this feature.

## Risk Matrix Definition

### Severity Scale (consumer SaaS — meal planning)

| Level        | Definition                                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Catastrophic | Cross-tenant plan data exposure or modification, or irreversible plan loss at scale.                                                        |
| Critical     | Single-user unauthorized access, unrecoverable plan corruption, or sustained core-flow outage (≥ 1 hour).                                   |
| Serious      | Recoverable but high-friction degradation: wrong nutrition shown as authoritative, duplicated entries, silent data loss on a bounded scale. |
| Minor        | User-visible annoyance: transient inconsistency, non-blocking validation error.                                                             |
| Negligible   | Cosmetic drift without integrity or privacy impact.                                                                                         |

### Likelihood Scale

| Level      | Definition                                                     |
| ---------- | -------------------------------------------------------------- |
| Frequent   | Expected under normal usage (daily).                           |
| Probable   | Expected occasionally (weekly).                                |
| Occasional | Seen rarely (monthly).                                         |
| Remote     | Possible under unusual conditions.                             |
| Improbable | Conceivable only under stacked failures or adversarial timing. |

### Risk Level Matrix

|              | Frequent     | Probable     | Occasional   | Remote      | Improbable  |
| ------------ | ------------ | ------------ | ------------ | ----------- | ----------- |
| Catastrophic | Unacceptable | Unacceptable | Unacceptable | Undesirable | Undesirable |
| Critical     | Unacceptable | Unacceptable | Undesirable  | Undesirable | Tolerable   |
| Serious      | Unacceptable | Undesirable  | Undesirable  | Tolerable   | Tolerable   |
| Minor        | Undesirable  | Tolerable    | Tolerable    | Tolerable   | Acceptable  |
| Negligible   | Tolerable    | Tolerable    | Acceptable   | Acceptable  | Acceptable  |

**Disposition rule**: `Unacceptable` MUST be reduced to `Undesirable` or lower before release. `Undesirable` MUST carry
explicit residual-risk acceptance.

## Operational States

| State             | Definition                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------------- |
| NORMAL            | Steady-state authenticated planning.                                                                        |
| DST-BOUNDARY      | Day/week transitions across daylight-saving changes, time-zone offsets and locale week starts.              |
| DEGRADED-RECIPE   | **Replaces DEGRADED-AI.** The recipe service is slow, erroring or partially answering the batch projection. |

### Hazards eliminated by simplification

Worth stating explicitly, because it is the strongest argument for the reconciled design: **four hazards disappeared
because the components that carried them were removed.**

| Removed component           | Hazard eliminated                                                     |
| --------------------------- | --------------------------------------------------------------------- |
| Redis summary cache         | HAZ-009 — stale totals after a missed invalidation                    |
| Stored nutrition rollup     | HAZ-009 (compounding) — a second source of truth going stale silently |
| Recurrence expansion        | HAZ-016 — duplicated future weeks                                     |
| Ingredient-manifest handoff | HAZ-018 — reuse assumptions diverging from grocery sync               |

## Residual Risk Acceptance

Fourteen hazards remain `Undesirable` and are accepted with the controls above. Two warrant explicit sign-off at the
release gate:

- **HAZ-020** (cross-tenant exposure) — Catastrophic × Improbable. Accepted with in-query owner predicates,
  indistinguishable `404` responses, integration tests from a second principal, audit logging, and a periodic access
  review.
- **HAZ-041** (logical-DB derivation drift) — Catastrophic × Improbable. Accepted with the import-free leaf module and a
  cross-stack parity test as a **release gate**. This one has a precedent in production (defect #119), which is why the
  control is a test rather than a convention.

## Domain Note (non-regulated)

This analysis intentionally avoids regulated-domain safety classifications. Meal Planning is assessed under consumer
software risk principles: trust, privacy, integrity, availability and cost.
