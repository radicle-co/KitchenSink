## Overview

Meal Planning lets an authenticated user create plans over a calendar date range, assign recipes to (day, meal-slot)
cells on web and mobile, see per-day and whole-plan nutrition derived from recipe-level data, and reuse a plan as a
template. It lights up the Home "This Week's Meals" widget that feature 001 already ships as a placeholder, and exposes
a read projection for grocery lists (007) and nutrition planning (009).

AI suggestions, auto-generation and waste optimization are **Phase 2**: they depend on feature 005, which does not
exist, and on a premium entitlement that cannot be enforced today. They are specified in the _Phase 2 Requirements_
section below and are excluded from every Phase-1 coverage obligation. The Phase-1 counterpart is REQ-CN-006 — those
surfaces must be **unreachable**, which is verifiable now (C-006-013).

> **REQ-019 verification corrected 2026-08-07: `Inspection` → `Test`.** The row claimed the localization rule was
> verified by human inspection. It is not, and was not even when the row was written: STS-008-A4 already specified it as
> a CI-executed machine check ("**No user-visible string literal exists outside `messages.ts`**"), and that check now
> exists and runs — a TypeScript-AST audit in
> `packages/apps/commise/features/meal-plan/src/__tests__/noUserVisibleLiterals.test.ts`, with a detector-teeth half
> that proves it can fail before the real-tree half is allowed to pass. ISO 29119 `Inspection` means a human reads the
> artifact; an executable assertion in a pipeline is `Test`. Left as `Inspection`, the row invited a reviewer to sign
> the requirement off by eye and let the audit rot unnoticed, and it made the by-method tallies at the foot of this
> file wrong.
>
> **Why REQ-023 is a new id and not another clause on REQ-019.** They fail independently and are caught by different
> checks: REQ-019 is about literals _in our source_ (AST audit over the package tree), REQ-023 is about a string the
> _server_ sent (a rendered value the literal audit cannot see, since `error.message` is a member expression, not a
> literal). Merging them would produce one id that is half-satisfiable and, per the atomicity discipline this document
> already applies to REQ-021/022 and REQ-NF-010, would hide exactly the failure that motivated the split.

## Assumptions

- Recipes assigned to a plan are readable by the planner **at assignment time**; 006 grants, widens and caches no recipe
  access. The recipe service remains the enforcement boundary.
- A user may have zero recipes. _(The May assumption that they always have a collection is dropped — the empty-recipe
  case is a real first-run state and is specified in the wireframes.)_
- Recipe nutrition may be **incomplete**, and that is a normal state, not an error: 001 models it explicitly with
  `isComplete`. 006 propagates partiality rather than assuming complete data. _(The May assumption that "nutritional
  data is available for all ingredients" is dropped — it was never true.)_
- Subscription entitlement is owned by 010. 006 consumes a check it does not implement — and, in Phase 1, does not ship
  the surfaces that would need one.
- Everything else inherits from 001.

## Glossary

| Term               | Definition                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Meal Plan          | An owner-scoped planning surface over a calendar date range with a selected set of meal slots. Owns its entries.                                                                |
| Meal Plan Entry    | One recipe assigned to one (date, meal-slot) cell, with servings and an optional note. References a recipe by id across a service boundary; copies no recipe data.              |
| Meal Slot          | One of `breakfast`, `lunch`, `dinner`, `snack`. A plan uses a chosen subset.                                                                                                    |
| Cell               | The intersection of one date and one meal slot within a plan's range. Holds at most one entry (REQ-CN-010); renders as either the `+` add affordance or exactly one card.       |
| Meal Plan Template | An owner-scoped set of (day offset, slot, recipe, servings) tuples derived from a plan and applicable to a new start date.                                                      |
| Day Nutrition      | Per-day macro totals with a completeness flag. **Derived at read time, never stored.**                                                                                          |
| Orphaned Entry     | An entry whose referenced recipe is no longer readable by the owner. Detected on read; excluded from totals.                                                                    |
