> **How this matrix keys requirements.** It does not reference `FR-NNN` at all. It keys on `REQ-NNN`
> from [`requirements.md`](./requirements.md), which is where the `FR`/`NFR`/`SC` mapping lives — so
> `FR-024` is reachable here only as REQ-032. The five matrices then chain mechanically: REQ-N ↔ SYS-N
> ↔ HAZ-N one-to-one, each SYS fanning out to two ARCH modules (`Contract/Policy` = 2N−1,
> `Runtime/Execution` = 2N), and each ARCH to one MOD of the same number.
>
> **Rows for REQ-032…REQ-041 (`spec.md` FR-024…FR-033) were added by hand on 2026-08-10**, following
> that scheme: SYS-032…SYS-041, ARCH-063…ARCH-082, MOD-063…MOD-082, HAZ-032…HAZ-041. Two deviations
> from the generator's output are deliberate and are described where they occur: the new Matrix C and
> Matrix D rows use the per-module `ITP-{ARCH}-A..D` / `UTP-{MOD}-A..E` numbering that
> `integration-test.md` and `unit-test.md` themselves define, rather than the older rows' one-technique
> stagger, so that every new id resolves to a test case of the same name. Matrix H's header was also
> repaired — it declared four columns against twelve-cell rows, so it did not render as a table at all.
